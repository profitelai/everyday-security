# BAK-006 · Databases are backed up with a consistent method, not by copying live files

## Why it matters
A database file that is being written while it is copied can produce a backup with old and new pages mixed together. SQLite's own documentation lists copying a file during an active transaction as a way to get a corrupt copy, and a database in write-ahead-log mode keeps recent changes outside the main file. Such a backup may look fine and fail only at restore time.

## How to test
Find the backup job and read what it does to the database.
```bash
grep -r -n -E 'rsync|cp |tar |restic backup|borg create' /etc/cron* /etc/systemd/system 2>/dev/null | head
```
A red flag is a file-level copy of a database directory or `.db` file with the application still running. Prove the copy is usable by restoring it somewhere and checking it:
```bash
sqlite3 restored.db 'PRAGMA integrity_check;'
```

## Pass criteria
Every database is backed up with a method that gives a consistent result: for SQLite the `.backup` command, the backup API, or `VACUUM INTO`; for PostgreSQL `pg_dump` or a base backup with WAL archiving (for point-in-time recovery); for MySQL or MariaDB `mysqldump --single-transaction` on InnoDB tables, or a physical tool made for it; or an atomic snapshot of everything the database writes. A restored copy passes the engine's integrity check.

## Fix
SQLite: `sqlite3 /path/live.db ".backup '/backup/live-$(date +%F).db'"`, then back up that copy. PostgreSQL: `pg_dump -Fc dbname > file`, and for larger databases set up continuous archiving. Dump to a file first, then include that file in the file backup. Keep the dump and the files from the same moment together.

## Risk and rollback
Dumps and backup commands add I/O load and can briefly slow the application; schedule them off-peak. Dumps hold sensitive data, so protect them like the database. Rollback: switch back to the previous job, but keep the new dump files until a restore of them has been verified.
