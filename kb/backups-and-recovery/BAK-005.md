# BAK-005 · Restores are tested regularly and the result is written down

## Why it matters
A backup is only proven when data has come back out of it. Jobs can report success while the archive is incomplete, corrupt, missing a directory, or unreadable without a key nobody has. The restore also tells you how long recovery really takes, which a plan cannot guess.

## How to test
Ask for the log of the latest restore test. If there is none, run one now in a scratch location, never over live data:
```bash
restic -r REPO snapshots --last
restic -r REPO restore latest --target /srv/restore-test
restic -r REPO check --read-data-subset=1/10
```
Then verify the restored data: open the application against a restored database copy, compare file counts and sizes with the source, and run the database's own integrity check. Record the date, which backup was used, how long it took, who did it, and what went wrong.

## Pass criteria
A full restore of at least one critical system has been performed within the last 90 days (a reasonable default, tighter for fast-changing data), using only documented steps and the off-host key. The result, the elapsed time and any fixes are recorded. Repository integrity checks run on a schedule.

## Fix
Put a restore drill on the calendar (quarterly is a common start) and keep a short log. Automate the cheap part: a scheduled integrity check, with a larger `--read-data-subset` slice each time so the whole repository is read over a cycle. Fix any gap the drill finds (missing path, missing key) and repeat the drill.

## Risk and rollback
The danger of a restore test is overwriting live data or exposing restored copies. Always restore to an isolated path or machine, restrict access to it, and delete it afterwards. Reading data back from remote storage may cost transfer fees; use subsets. Nothing in the test changes production, so rollback is deleting the scratch copy.
