# BAK-004 · An attacker who controls the server cannot delete or alter its backups

## Why it matters
Attackers who gain a foothold commonly go after backups first, since removing them turns an incident into an unrecoverable loss. If the production host holds credentials that can delete or overwrite the backup store, then whoever takes the host can erase the backups too. Backups must be reachable for writing, not for destruction.

## How to test
1. On the production host, find the credentials the backup job uses (environment file, config, SSH key, cloud access key).
2. Work out what those credentials may do: can they delete objects, prune a repository, empty a bucket, or reach the storage's admin console?
3. On a scratch repository or test bucket (never the real one), try the destructive operation with those same credentials, for example deleting a test object or running the tool's forget/delete command, and confirm it is refused.
4. For object storage with a lock, inspect the configuration, for example on S3:
```bash
aws s3api get-object-lock-configuration --bucket BACKUP_BUCKET
aws s3api get-bucket-versioning --bucket BACKUP_BUCKET
```

## Pass criteria
The credentials held by the production host can add new backups but cannot delete or overwrite old ones. This is enforced by the storage or by a separate machine (append-only access, locked or immutable objects, or a pull model where the backup server fetches data and production holds no write access to it). Deletion and pruning use different credentials kept off the production host.

## Fix
Options, simplest first: run a restic rest-server with `--append-only`; give a borg client an SSH key restricted to `borg serve --append-only --restrict-to-path ...`; enable Object Lock with versioning on the bucket; or have a backup host pull the data over SSH. Do pruning from a trusted admin machine, not from the server being protected.

## Risk and rollback
Append-only and locked storage cannot be cleaned up from the client, so space grows until a privileged prune runs, and a long lock retention set by mistake cannot be shortened (in S3 compliance mode not even the root user can delete a locked version). Test the lock settings on a throwaway bucket first. Rollback for append-only is restoring the previous access method; locked objects wait out their retention.
