# BAK-007 · Retention keeps old restore points, not only yesterday's

## Why it matters
Many problems are noticed late: slow data corruption, a bad import, a deleted record someone asks about next month, or malware that sat quietly for weeks. If the job overwrites or prunes everything older than a few days, every restore point may already contain the damage. Keeping restore points of several ages gives you something clean to go back to.

## How to test
List what restore points actually exist and how far back they go:
```bash
restic -r REPO snapshots
borg list REPO
```
Then read the pruning command or retention setting (for restic, the `--keep-*` options of `forget`) and the storage lifecycle rules, if any, that expire old objects.

## Pass criteria
Retention is written down and covers several tiers, for example recent dailies, a number of weeklies and monthlies, and a yearly point where the data justifies it. The oldest available point is older than the longest time a problem could realistically go unnoticed, and it respects any legal duty to keep or delete records.

## Fix
Choose a policy and apply it, for example with restic: `restic forget --keep-daily 14 --keep-weekly 8 --keep-monthly 12 --prune`. Run it first with `--dry-run` and read the list of what it would remove. Run pruning from a trusted admin host (see BAK-004).

## Risk and rollback
Longer retention costs more storage and keeps personal data for longer, which can conflict with deletion obligations, so set the period deliberately. Pruning is permanent: a wrong policy deletes restore points that cannot be recovered. Always dry-run first and keep a separate copy until the new policy has been observed working.
