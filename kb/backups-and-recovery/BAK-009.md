# BAK-009 · Mail, uploaded files and configuration are recoverable, not only the database

## Why it matters
Rebuilding a service needs more than its database. User uploads, mailboxes, certificates and keys, application settings, web server and mail server configuration, scheduled jobs and the code that deploys it all are state. Backing up only the database often leaves a system that restores but cannot run, or has lost every attachment and message.

## How to test
1. Inventory where the state lives:
```bash
du -sh /var/www/*/uploads /var/mail /var/vmail /home/*/Maildir /etc /var/lib/docker/volumes 2>/dev/null
docker volume ls 2>/dev/null
```
Adjust paths to your layout.
2. Check each location is in the backup selection, for example `restic -r REPO ls latest | grep -E '/etc/|Maildir|uploads' | head`.
3. Check that configuration and infrastructure code (server config, deployment scripts, infrastructure templates) live in a version-controlled repository that is itself backed up or hosted off the server.

## Pass criteria
Every location holding user files, mail and configuration appears in the latest backup, and a spot-check of a recent mail message and an uploaded file in a restore succeeds. Configuration and infrastructure code are in version control with history, and secrets are excluded from the repository but recoverable from the encrypted backup.

## Fix
Add the missing paths to the backup selection. Put server configuration and deployment code under version control and push it to a hosted repository, keeping secrets out of it. Include container volumes and any data directory outside the usual places, and exclude only caches and rebuildable data.

## Risk and rollback
Mail and upload directories can be large, so first estimate storage and transfer time. Never commit passwords or private keys to a repository; if one is committed, rotate it, not only delete it. Rollback: remove the added path from the selection; existing snapshots stay unchanged.
