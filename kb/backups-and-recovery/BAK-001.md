# BAK-001 · Backups run on a schedule and a missed or failed run raises an alert

## Why it matters
A backup job that quietly stopped months ago looks exactly like one that works until the day you need it. The usual causes are dull ones (full disk, expired credential, changed path), and they are only caught if somebody or something is told when a run fails or does not happen at all.

## How to test
```bash
systemctl list-timers --all | grep -i backup
journalctl -u backup.service --since '3 days ago' --no-pager | tail -20
crontab -l; ls /etc/cron.d /etc/cron.daily
```
Adjust the unit name to your setup. Then find where a failure is reported: an email, a chat message, or a monitoring service. Confirm that the date of the newest backup in the storage is recent, and that the alert fires when no success signal arrives in the expected window (a "heartbeat" check, not only an error mail).

## Pass criteria
There is a scheduled job with a fixed frequency that suits the data, the latest successful run is within that interval, and a missing or failed run notifies a person who will see it. The success signal is sent only when the whole job, including the upload, completed.

## Fix
Run the backup from a systemd timer or cron with a non-zero exit on any error. At the end of a successful run, send a ping to a heartbeat monitor that alerts if the ping does not arrive on time. Also alert on the repository's age, for example from the newest snapshot timestamp.

## Risk and rollback
A noisy alert gets ignored, so tune the grace window to the job's normal duration. Adding a monitor does not change the backup itself; rollback is removing the ping line from the job.
