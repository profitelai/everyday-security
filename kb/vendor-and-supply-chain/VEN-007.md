# VEN-007 · New packages are vetted for typosquatting, install scripts and maintainer health before adoption

## Why it matters
Public registries accept anyone's code. Attackers publish packages with names one typo away from popular ones, take over abandoned packages or maintainer accounts, or add a malicious update to a legitimate package. Many ecosystems can run code on the developer's or build server's machine at install time (npm preinstall and postinstall scripts, Python setup scripts), so the damage can happen before the app ever runs, with access to your tokens. A short vetting habit before adding a dependency, and install settings that limit what it can do, remove most of the easy attacks.

## How to test
1. Review how the last three new dependencies were chosen. Ask: was the name typed from an official page (not guessed or suggested by a chat assistant), is the package widely used, and is it really needed?
2. Inspect a candidate or an existing package.
```bash
npm view PACKAGE name version maintainers time.modified repository.url dist.tarball
npm audit signatures                       # verifies registry signatures and provenance where published
scorecard --repo=github.com/OWNER/REPO    # OpenSSF Scorecard: maintained, reviewed, signed releases, etc.
```
   Read: age and release history, number of maintainers, whether the repository link matches the registry page, whether the repository is archived, and any sudden change of maintainer.
3. Find packages in the installed tree that run code on install.
```bash
for f in node_modules/*/package.json node_modules/@*/*/package.json; do
  jq -r 'select(.scripts.preinstall or .scripts.install or .scripts.postinstall) | .name' "$f"
done
npm config get ignore-scripts
```
4. If you use private package names (for example an internal library), confirm the same name is not claimed on the public registry, and that the project uses a scope or an explicit registry mapping so the public one is never fetched in its place (dependency confusion).
5. Check that CI installs run with minimal credentials (see VEN-008) and that the install command is the locked one from VEN-005.

## Pass criteria
There is a written rule for adding a dependency (official source, maintenance signs, necessity) and recent additions follow it. Install scripts are disabled in CI and production builds unless a listed package needs them, and each exception is reviewed. Package signatures verify where the ecosystem supports it. Internal package names cannot be taken over on the public registry. Packages that are archived, unmaintained or have lost their maintainers are on a replacement list.

## Fix
Set `ignore-scripts=true` in the project `.npmrc` for CI and production installs and run the few builds that need scripts explicitly (for example `npm rebuild PACKAGE`). Prefer fewer, well-known packages; copy a ten-line function rather than adding a package. Use a private registry or proxy for tier 1 systems if your team can run one. Add the vetting rule to the pull request template. Report suspicious packages to the registry's security team.

## Risk and rollback
Turning off install scripts can break packages that download binaries or compile code on install; the build will fail loudly, so test on a branch first. Scorecard results are signals, not verdicts: a low score on a small, careful project is not proof of a problem. Rollback: remove `ignore-scripts` for the single affected package build, document why, and keep the setting elsewhere.
