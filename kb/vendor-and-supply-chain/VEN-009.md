# VEN-009 · Third-party scripts on the website are inventoried, integrity-checked where possible, and tag manager access is controlled

## Why it matters
Every script loaded from another company runs with the full power of your page: it can read forms, steal session data, change checkout fields or inject ads. If that company is breached, or the file is replaced on its server or content delivery network, every site that loads it is attacked at once. Subresource Integrity (SRI) lets the browser refuse a file whose hash does not match the one you approved. It works only for files that do not change, so analytics and tag-manager scripts need other controls: a short list of approved sources, a Content Security Policy (HDR-002), and tight control over who can publish through the tag manager.

## How to test
1. List external scripts and styles in the delivered HTML.
```bash
curl -s https://example.com/ | grep -oiE '<(script|link)[^>]+(src|href)="https?://[^"]+"[^>]*>' | sort -u
curl -s https://example.com/ | grep -oiE '<script[^>]+src="https?://[^"]+"[^>]*>' | grep -vi 'integrity='
```
   Repeat for the checkout, login, contact and admin pages, which matter most.
2. Scripts loaded at run time are missed by static HTML. Open the browser developer tools Network tab, reload, filter by JS, and note every third-party domain; the Content-Security-Policy-Report-Only header can collect the same list from real visitors.
3. Check that each file loaded from a content delivery network has `integrity="sha384-..."` and `crossorigin="anonymous"`, and that the hash is right.
```bash
curl -s https://cdn.example.net/lib.min.js | openssl dgst -sha384 -binary | openssl base64 -A
```
   Compare with the value in the page after the `sha384-` prefix.
4. Compare the inventory of scripts with the vendor inventory (VEN-001). Each script's domain should map to a vendor with an owner and a reason; remove any that nobody can explain.
5. If a tag manager is used, review its users: who can publish, whether publishing needs approval, whether custom HTML or JavaScript tags are allowed, whether MFA is on for every user, and whether former staff or agencies still have access. Check the version history for changes nobody remembers.
6. On pages with payment or login forms, check that only the minimum scripts load.

## Pass criteria
An up-to-date list of third-party scripts exists, each with an owner and purpose. Static third-party files that rarely change either use SRI or are self-hosted from your own server at a pinned version. Scripts that cannot use SRI (tag managers, analytics, chat, ads) are limited to the smallest set, and the Content Security Policy restricts which origins may load scripts. Tag manager publishing is limited to named people with MFA, and custom code tags need approval. Sensitive pages load fewer third-party scripts than the rest of the site.

## Fix
Add SRI attributes to static CDN files, or download the file, host it yourself and update it through your normal dependency routine (VEN-006). Delete unused tags and trackers. Add or tighten the Content Security Policy, starting in report-only mode. In the tag manager, enable approval workflow, remove stale users and block unreviewed custom HTML tags. Keep checkout and login pages free of marketing tags where possible. Review the list whenever marketing adds a tool.

## Risk and rollback
A wrong SRI hash makes the browser block the script, which can break the page, and any legitimate update of the file will also be blocked until you change the hash; test on staging and update the hash with the file. A strict Content Security Policy can block tools marketing relies on, so start in report-only mode. Removing tags can stop tracking or ads, so confirm with the owner first. Rollback: remove the `integrity` attribute or revert the policy or tag manager version to the previous published one.
