# VEN-008 · CI/CD pipelines use least-privilege, short-lived secrets and pinned third-party actions

## Why it matters
Your build pipeline holds the keys to production: deploy keys, cloud credentials, registry tokens. It also runs other people's code (build plugins, marketplace actions, test dependencies). A compromised third-party action or a leaked token lets an attacker push their own code to your site without ever touching your servers. GitHub's hardening guide and the OWASP CI/CD cheat sheet both stress least privilege, careful handling of secrets, and pinning outside code. SRV-009 covers secrets in repositories and rotation after exposure; this check covers the pipeline itself.

## How to test
Examples use GitHub Actions; apply the same questions to GitLab CI, Jenkins or hosting-provider deploy hooks.
```bash
grep -rn 'uses:' .github/workflows | grep -vE '@[0-9a-f]{40}'    # third-party actions not pinned to a full commit SHA
grep -rn -B1 -A6 'permissions' .github/workflows                  # is GITHUB_TOKEN limited? (default may be broad)
grep -rn 'pull_request_target' .github/workflows                  # runs with secrets on code from forks: review closely
grep -rnE 'AKIA|ghp_|BEGIN (RSA|OPENSSH) PRIVATE|password *[:=]' .github/workflows
gh secret list
gh secret list --org ORG        # if an organization is used
```
Then review by hand:
1. For each secret: what it can do, who created it, when it was last rotated, and whether the owner is still with the business. Personal access tokens tied to a person are a finding.
2. Whether long-lived cloud keys could be replaced by short-lived credentials issued per run (OpenID Connect trust with the cloud provider).
3. Deploy keys and API tokens: read-only unless write is required, scoped to one repository or one environment, with an expiry date.
4. Whether secrets are available to pull-request builds from forks or to every branch, instead of only protected branches or approved environments.
5. Whether logs print secrets (a `set -x` or `env` dump) and whether runners are shared with other projects.
6. Scan history for leaked values with a secret scanner such as `gitleaks detect` or `trufflehog git file://.`.
7. Who can edit the workflow files and merge to the default branch, and whether that requires review.

## Pass criteria
Third-party actions are pinned to full commit SHAs (or a reviewed internal fork). Workflow token permissions are set to the minimum per job. No secret is in a workflow file or repository history; deploy secrets are limited to protected branches or approved environments and never exposed to untrusted fork code. Each secret has an owner, a purpose, the least scope needed and a rotation date; tokens tied to departed staff are revoked. Changes to workflows require review.

## Fix
Pin actions by SHA and let VEN-006 update them. Add a top-level `permissions: contents: read` and raise it per job only when needed. Move secrets into the platform's secret store or environment-level secrets with required approval. Replace long-lived keys with short-lived credentials where the provider supports it. Create machine accounts or app tokens for automation instead of personal ones. Rotate anything that may have been exposed (SRV-009) and enable the platform's secret scanning and push protection.

## Risk and rollback
Rotating or narrowing a token can break deployments, so change one secret at a time, outside a release window, and keep the old one valid until the new one is confirmed working. Pinning to SHAs means you must update deliberately. Rollback: restore the previous secret value from the vault, revert the workflow change, and re-run the pipeline.
