# VEN-005 · Dependencies are inventoried with committed lockfiles, pinned versions and a producible SBOM

## Why it matters
You cannot answer "are we affected?" when a new flaw or a poisoned package is announced unless you know exactly which components, at which versions, are running in production. A lockfile records the exact version of every direct and indirect dependency, so what you test is what you ship. Without it, an install tomorrow can silently pull a different, possibly malicious, release. A software bill of materials (SBOM) is a machine-readable list of those components; CISA and the NTIA describe it as a basic building block for supply-chain risk management. At small-business scale, the lockfile plus a generated SBOM is enough. APP-009 and SRV-011 cover scanning that list for known vulnerabilities; this check covers having a trustworthy list and reproducible installs.

## How to test
Run in each repository that is deployed.
```bash
git ls-files | grep -E '(package-lock\.json|npm-shrinkwrap\.json|yarn\.lock|pnpm-lock\.yaml|composer\.lock|poetry\.lock|Pipfile\.lock|requirements.*\.txt|Gemfile\.lock|go\.sum)$'
grep -nE '"[^"]+": *"(\*|latest|>=?[0-9])' package.json        # unbounded ranges
grep -n '^FROM' Dockerfile*      # flag any image with :latest or with no tag or digest
```
Then prove the lockfile is honored and complete:
```bash
npm ci && git status --porcelain          # fails if package.json and the lock disagree
pip install --require-hashes -r requirements.txt   # only if hashes are used
```
Produce an SBOM and confirm it lists real packages with versions:
```bash
syft dir:. -o cyclonedx-json > sbom.json    # any stack
npm sbom --sbom-format cyclonedx            # npm 9 or later
jq '.components | length' sbom.json
```
For a WordPress or other CMS site, export `wp plugin list --format=csv` and `wp theme list --format=csv` and keep it with the inventory. Confirm the deployment pipeline installs from the lockfile (`npm ci`, `composer install`, not `npm install` or `composer update`).

## Pass criteria
Every deployed project has its lockfile in version control. Deploys use the locked install command. Container base images and CI actions are pinned to a specific version or digest, not `latest`. An SBOM (CycloneDX or SPDX) can be produced on demand in under an hour and is kept for each release of tier 1 systems. For CMS sites, a current list of plugins, themes and versions exists.

## Fix
Commit the lockfile, change deploy scripts to the locked install command, and replace `latest` tags with explicit versions (a digest is stronger). Add an SBOM generation step to the release build and archive the file. Hash-pin Python requirements with `pip-compile --generate-hashes` or your tool's equivalent when you can accept the maintenance. Feed the SBOM to the scanner you use for APP-009.

## Risk and rollback
Pinning means you must actively update (VEN-006), or you will freeze known-vulnerable versions. A first `npm ci` may fail on an out-of-date lockfile; regenerate it on a branch and test. Rollback: revert the commit that changed the lockfile or pin, and redeploy the previous build.
