# CLD-008 · Public storage buckets and open sharing links are reviewed and blocked by default

## Why it matters
Object storage and file-sharing services make it one click to publish a file to the whole internet, and that setting then stays in place long after anyone remembers it. Exposed buckets and "anyone with the link" folders are a routine source of leaked customer lists, invoices, database dumps and backups, and search engines and scanners index them. A website's image bucket may legitimately be public, but it should be a deliberate, narrow exception.

## How to test
List every bucket, container, shared drive and sharing link that can be read without signing in, and decide for each whether it is meant to be public.
- AWS S3: account level `aws s3control get-public-access-block --account-id ACCOUNT_ID`; per bucket `aws s3api get-public-access-block --bucket BUCKET` and `aws s3api get-bucket-policy-status --bucket BUCKET` (look for `IsPublic`); `aws s3api get-bucket-acl --bucket BUCKET`.
- Google Cloud Storage: `gcloud storage buckets describe gs://BUCKET` (look for the public access prevention setting), and `gcloud storage buckets get-iam-policy gs://BUCKET` (look for `allUsers` or `allAuthenticatedUsers`).
- Azure: `az storage account show --name ACCOUNT --query allowBlobPublicAccess`.
- Anonymous probe from outside your accounts, for example `curl -s -o /dev/null -w '%{http_code}\n' https://BUCKET.s3.amazonaws.com/` or a listing request against the bucket address; an XML object listing means anyone can list the contents.
- Google Workspace: Admin console, Apps, Google Workspace, Drive and Docs, Sharing settings: is sharing outside the organisation allowed, and are "anyone with the link" defaults on? The Drive audit log shows files with public visibility.
- Microsoft 365: SharePoint admin center, Policies, Sharing: check whether "Anyone" links are allowed, and review the sharing reports.
- Code host: public repositories and releases, and public package or container registries owned by the company.
Also search the web for your domain names with terms such as "index of" to see what is exposed.

## Pass criteria
Account-level public access blocking is on (S3 Block Public Access, Google Cloud public access prevention, Azure public blob access disabled) except for named buckets with a recorded reason and a content review. No bucket or share that holds customer data, backups, logs or credentials is readable without sign-in. File-sharing defaults are limited to named people or the organisation, "anyone with the link" is off or confined to a documented use with expiry, and anonymous bucket listing is disabled everywhere.

## Fix
Turn on the account-level block first, then open specific exceptions for the buckets that serve a website, ideally behind your CDN rather than directly. Move private files to private buckets and serve them with short-lived signed links. Change sharing defaults in Google Workspace and SharePoint, convert open links to named sharing, and set expiry on links that must stay. Delete or move anything sensitive that was exposed, and treat anything that was public as seen by others: rotate any credentials it contained and consider your breach duties under the privacy-compliance pillar.

## Risk and rollback
Blocking public access breaks websites, downloads and email images that fetch directly from a bucket, so inspect the web server and CDN settings and test on a staging copy first. Changing sharing defaults can break links already sent to customers. Rollback: remove the block on the specific bucket, or re-create the link with the right audience, from your saved export of the old configuration.
