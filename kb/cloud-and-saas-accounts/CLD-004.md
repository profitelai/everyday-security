# CLD-004 · API keys and tokens are scoped, expire or are rotated, and are kept out of code repositories

## Why it matters
Scripts, plugins and integrations authenticate with long-lived keys that bypass MFA. A key with full account rights that leaks into a repository, a chat or a log gives an attacker the same power as an admin, and automated scanners find exposed keys within minutes of a public push. Scoped, expiring keys limit what a leak can do, and a rotation habit proves you know where each key is used and can replace it in a hurry.

## How to test
1. Inventory the keys. Cloudflare: Manage Account, API Tokens and My Profile, API Tokens (check that the legacy Global API Key is not used by anything). GitHub: personal Settings, Developer settings, Personal access tokens; for an organisation, Settings, Personal access tokens lists active fine-grained tokens. Stripe or another payment provider: the developer area, API keys, and look for unrestricted secret keys. AWS: `aws iam list-access-keys --user-name USER`, `aws iam get-access-key-last-used --access-key-id KEYID`, or the credential report (`aws iam generate-credential-report`, then `aws iam get-credential-report --query Content --output text | base64 -d`). Google Cloud: `gcloud iam service-accounts keys list --iam-account=SA_EMAIL --managed-by=user`. Email-sending providers: the API keys page.
2. For each key record the owner, what it is used for, its permissions and resource scope, whether it has an expiry or IP restriction, the creation date and the last-used date.
3. Scan the code. For each repository, including its full history: `trufflehog git file://$PWD --only-verified` (or another secret scanner such as Gitleaks). On GitHub confirm secret scanning and push protection are on for the repository or organisation and review open alerts.
4. Search deployed locations that are not repositories: shared documents, chat channels, wiki pages, CI settings pasted as plain text, and `.env` files committed or backed up to web-served folders.
5. Verify a Cloudflare token still works as intended without exposing it: `curl -s https://api.cloudflare.com/client/v4/user/tokens/verify -H "Authorization: Bearer $TOKEN"` returns status `active` for a valid token.

## Pass criteria
Every key is on the inventory with an owner. No key grants more than its job needs: restricted or scoped keys are used instead of root, global or unrestricted keys, and IP restrictions and expiry dates are set where the service supports them. Keys are rotated on a stated schedule (a year at most is a reasonable default for a small business; shorter for high-power keys) and immediately after a person with access leaves or after any suspected exposure. Unused keys are deleted. Scanning of the full repository history finds no live secret, and any secret that was ever committed has been revoked, not just deleted from the latest commit. Secrets live in a secrets manager or the platform's protected environment variables.

## Fix
Replace broad keys by scoped ones: in Cloudflare create a token for a single zone and permission; in Stripe use restricted keys; on GitHub prefer fine-grained tokens and set an organisation policy for maximum lifetime and approval; on cloud platforms prefer attached roles and temporary credentials over stored access keys. Move values into a secrets manager or protected environment variables, turn on secret scanning and push protection, and add a pre-commit scanner. Revoke and re-issue every key that appeared in a repository, because history can be copied. Add a rotation date to the inventory.

## Risk and rollback
Rotating a key breaks anything still using the old one, so create the new key, deploy it, confirm the integration works, and only then revoke the old one. Rewriting git history does not make a leaked key safe; revocation is the real fix. Rollback: until the old key is revoked it can be put back into the configuration; once revoked, issue another new key rather than trying to restore it.
