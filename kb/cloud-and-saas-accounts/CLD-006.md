# CLD-006 · Third-party app and OAuth grants to company data are limited and reviewed

## Why it matters
When someone clicks "Sign in with Google" or "Allow access" for a scheduling tool, mail plug-in or AI assistant, the app receives a token that can read mail, files or repositories, and that token keeps working after the password changes and often without MFA. Attackers use fake apps to trick staff into granting access, and genuine apps can be breached or sold. Because no password is involved, these grants are invisible unless somebody lists them.

## How to test
List the grants, then ask what each one is for.
- Google Workspace: Admin console, Security, Access and data control, API controls, Manage app access. Open the list of accessed apps (it shows the user count for each), and note the default setting for apps that have not been configured. The default allows users to authorise any third-party app.
- Microsoft 365: Entra admin center, Enterprise applications, Consent and permissions, User consent settings; then the All applications list, and for each app that is not Microsoft's, its Permissions tab. Note whether an admin consent workflow exists.
- GitHub: organisation Settings, Third-party access (OAuth app policy and installed GitHub Apps); each member's personal Settings, Applications, Authorized OAuth Apps.
- Cloudflare, Stripe, your cloud host and the code host: look in the account's integrations or connected apps section.
For every app with mail, drive, calendar, repository or admin-level permission, find an owner and a business reason. Check last-used dates and look for apps nobody recognises, apps from unverified publishers and apps granted by former staff.

## Pass criteria
User consent is switched off or limited to verified publishers and low-impact permissions, with an admin approval route for anything else. Every app with access to mail, files, repositories or admin functions is on a list with a named owner and a stated purpose. Unknown, unused and former-staff grants are removed. The list is reviewed at least twice a year (a cadence we suggest, not a standard) and after any phishing incident.

## Fix
Set the consent policy: Google, restrict unconfigured third-party apps to sign-in-only or block them and mark approved apps as trusted; Microsoft, choose "allow user consent for apps from verified publishers, for selected permissions" or disable user consent and enable the admin consent workflow; GitHub, turn on OAuth app access restrictions for the organisation. Revoke grants you cannot justify. Record each approved app in the inventory of CLD-010.

## Risk and rollback
Blocking or revoking an app breaks whatever depended on it (a booking page, a CRM sync, a mail-sending integration), so check last-used dates and ask the owner first, and revoke in a quiet period. Changing the consent policy affects only future consents; existing grants stay until revoked. Rollback: set the app back to trusted or re-approve it, and the user re-authorises when prompted.
