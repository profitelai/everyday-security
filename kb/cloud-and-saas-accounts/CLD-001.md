# CLD-001 · Every administrator account uses MFA, and the most powerful ones sign in with phishing-resistant methods

## Why it matters
An administrator login at your email suite, DNS and CDN provider, code host, cloud host or payment provider can change everything the business runs on. A stolen password alone is then enough for an attacker to read all mail, redirect the domain or empty a storage bucket. A second factor stops most password theft, but codes sent by text message or typed from an app can still be talked out of a person on a fake login page. Passkeys and hardware security keys are bound to the real site address, so a look-alike page cannot use them.

## How to test
First list every account that holds an owner, super admin, global admin or billing role in each service. Then check, per service, whether MFA is enforced by policy (not merely available) and which methods the admin actually uses. Menu names change; look for the nearest equivalent.
- Google Workspace: in the Admin console open the Security area, then Authentication, then 2-step verification. Confirm enforcement is on for the organisation or for the organisational unit that holds admins, and look at the allowed methods. The user reports in the Reporting area show who is enrolled and who is enforced.
- Microsoft 365: in the Entra admin center open Conditional Access and look for a policy that targets directory roles and requires an authentication strength (the built-in phishing-resistant strength is the strongest). Check it is on, not report-only.
- GitHub: organisation Settings, Authentication security: is "Require two-factor authentication" on, and is "Only allow secure two-factor methods" on? The People page shows each member's status. With the GitHub CLI as an owner: `gh api orgs/ORG --jq .two_factor_requirement_enabled` and `gh api 'orgs/ORG/members?filter=2fa_disabled' --jq '.[].login'`.
- Cloudflare: My Profile, Authentication shows the admin's own methods; Super Administrators can enforce 2FA for all members of the account.
- Other services (VPS or cloud host, payment provider, email-sending provider, domain registrar): open the account security page and read the enrolled methods.
Write the result in a table: service, admin, method (passkey or security key, authenticator app, text message or email code, none).

## Pass criteria
Every administrator account in every service has MFA enforced by policy, with no exceptions for "just this once". Text message, voice call and email-only codes are not the sole factor for any administrator. The accounts that can take over the business (the primary email suite super admin, the DNS and CDN owner, the registrar, the code-host owners, the cloud root or owner, the payment account owner) use passkeys or hardware security keys, with at least two registered per person and recovery codes stored offline.

## Fix
Turn on enforcement in each service starting with administrators, then everyone else. Register two security keys (or passkeys on two devices) per admin and print or store the recovery codes in the safe described in CLD-002. In Microsoft 365 create the Conditional Access policy in report-only mode first, review the sign-in log, then switch it on. On GitHub turn on "Only allow secure two-factor methods" after members have moved off text messages. Where a service supports only authenticator codes, use that, and put the service on your review list for when keys become available.

## Risk and rollback
Enforcement can lock out an admin who has no second factor ready, so enrol first and enforce second, and keep the break-glass path from CLD-002 working before you tighten anything. On GitHub, organisation members without 2FA lose access and outside collaborators are removed until they enable it; warn people first. Rollback: switch enforcement from "required" back to "optional" or put the Conditional Access policy back into report-only mode, then fix the enrolment gap and re-enable.
