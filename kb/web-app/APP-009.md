# APP-009 · Libraries, plugins and frameworks are scanned for known vulnerabilities and kept updated

## Why it matters
Most of a modern site is code somebody else wrote: framework, packages, CMS plugins, themes. When a flaw in one of them is published, attackers scan the internet for sites still running the old version, often within days. Vulnerable and outdated components are category A06 of the OWASP Top 10:2021, and abandoned plugins are a typical way small sites get taken over.

## How to test
Run a scanner against the project folder (or the deployed copy) and list what the CMS thinks is out of date. Use the tool that matches the stack.
```bash
osv-scanner scan -r .                 # any ecosystem with a lockfile
npm audit --omit=dev                  # Node
composer audit                        # PHP
pip-audit -r requirements.txt         # Python
wp core check-update && wp plugin list --update=available   # WordPress (WP-CLI)
```
Then review by hand: when was each plugin or theme last updated by its author, is anything installed but unused, and is a lockfile committed so that the scanned versions are the deployed ones? Also confirm the runtime itself (PHP, Node, Python) is still supported by its maintainers.

## Pass criteria
No known high or critical vulnerability is left in components that run in production, or each exception is written down with a reason and a date to revisit. Lockfiles are in version control. Unused plugins and themes are removed, not merely deactivated. Unsupported runtimes are not in use. A scan runs on a schedule or on each change.

## Fix
Update the affected packages to patched versions, or replace abandoned ones. Turn on automated update pull requests (Dependabot or Renovate) and a scheduled scan in CI. Keep a short written patch window, for example critical issues within days. For CMS sites, enable automatic security updates for core and trusted plugins where the vendor supports it.

## Risk and rollback
Updates can break a layout, a plugin interaction or an API. Take a backup or snapshot first, update on a staging copy when possible, and update one major component at a time. Rollback: restore the backup or reinstall the previous pinned version from the lockfile, then schedule a fix with a compensating control (for example blocking the affected route).
