# APP-004 · State-changing requests are protected against cross-site request forgery

## Why it matters
Browsers attach a site's cookies to any request to that site, including ones triggered from another page. Without a check, a hostile page can make a logged-in visitor's browser submit a form (change email, transfer, delete) without their knowledge. Anti-CSRF tokens, plus `SameSite` cookies, let the server tell its own forms from forged ones.

## How to test
Use a test account on a harmless action such as changing a display name. Log in, then replay the request without the token.
```bash
# Replay a state-changing POST with the valid session cookie but NO csrf token
curl -s -o /dev/null -w '%{http_code}\n' -X POST -b 'session=YOUR_TEST_COOKIE' \
  -d 'display_name=csrf-probe' https://example.com/account/profile
# Cookie flags on the session cookie
curl -sI https://example.com/login | grep -i '^set-cookie'
```
Also confirm that no state change is performed by a GET request (links, images, or `GET /delete?id=...`) and that JSON endpoints reject form-encoded bodies.

## Pass criteria
The tokenless POST is rejected (typically 403 or 419) and the name does not change. Forms include a per-session or per-request token that is checked on the server. The session cookie sets `SameSite=Lax` or `Strict`. Changes never happen through GET.

## Fix
Turn on the framework's CSRF middleware (Django, Laravel and Rails ship one) or implement the synchronizer-token pattern. Set `SameSite=Lax` on session cookies as defence in depth, and check the `Origin` header on sensitive routes. Move any state change off GET.

## Risk and rollback
Forms and AJAX calls that lack the token start failing, including mobile-app and webhook endpoints that legitimately post without a browser session; exempt those narrowly and authenticate them another way (signed secret). Rollback: disable the middleware for the one failing route, not globally.
