# APP-007 · Passwords are stored with a slow, salted hash such as Argon2id

## Why it matters
If the user table leaks (backup copy, SQL injection, stolen laptop), the way passwords are stored decides whether attackers get logins or only unreadable strings. Fast hashes (plain MD5, SHA-1, SHA-256) can be guessed billions of times per second. Password-specific algorithms are deliberately slow and memory-hungry and add a unique salt for each user. Cryptographic failures is category A02 of the OWASP Top 10:2021.

## How to test
Inspect how the code hashes passwords and what the stored values look like. Do not print or copy real hashes; look only at the prefix.
```bash
# Code: which functions touch passwords?
grep -rnE "password_hash|password_verify|bcrypt|argon2|scrypt|pbkdf2|md5\(|sha1\(|hash\('sha|createHash" --include='*.php' --include='*.py' --include='*.js' --include='*.ts' . | grep -v node_modules
# Data: count the hash formats in use (example for a MySQL/MariaDB users table)
mysql -e "SELECT SUBSTRING(password_hash,1,8) AS prefix, COUNT(*) FROM users GROUP BY 1;" appdb
```
Prefixes tell you the scheme: `$argon2id$` is Argon2id, `$2y$` or `$2b$` is bcrypt. A 32-, 40- or 64-character hex string is a fast hash, and plain text is the worst case.

## Pass criteria
All stored values use Argon2id (OWASP minimum: 19 MiB memory, 2 iterations, 1 lane), or scrypt with cost 2^17, block size 8 and 1 lane, or bcrypt with work factor 10 or higher on older systems. Each hash has its own random salt, which standard libraries add themselves. No plain text, reversible encryption or fast unsalted hashes. Verification uses the library's own compare function.

## Fix
Use the platform's password API (PHP: `password_hash($pw, PASSWORD_ARGON2ID)` where Argon2 support is compiled in, otherwise `PASSWORD_DEFAULT`; the `argon2-cffi` package for Python; maintained `argon2` or `bcrypt` packages for Node). Upgrade old hashes at the next successful login (`password_needs_rehash` in PHP) rather than forcing a reset. Remember that bcrypt ignores input after 72 bytes.

## Risk and rollback
Stronger parameters cost server CPU and memory on every login; benchmark on the production machine and keep login latency reasonable. Rolling upgrade at login means both formats exist for a while, so keep the old verifier until the table is migrated. Rollback: lower the cost setting; never go back to a fast hash.
