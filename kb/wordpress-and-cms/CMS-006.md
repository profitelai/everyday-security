# CMS-006 · Dashboard file editing is disabled, and wp-config.php is unreadable from the web with unique secret keys

## Why it matters
By default an administrator can edit plugin and theme PHP files from inside the dashboard. The WordPress hardening guide notes this is often the first thing an attacker uses after getting a login, because it turns a stolen password into running code. The file `wp-config.php` holds the database password and the secret keys and salts that protect login cookies, so reading it gives an attacker the database, and weak or default keys make forged sessions easier. Editor swap files, `.bak` copies and debug logs left in the web root are a common way these secrets leak.

## How to test
```bash
cd /var/www/example
wp config get DISALLOW_FILE_EDIT                 # expect 1 or true
wp config get DISALLOW_FILE_MODS                 # optional; true also blocks dashboard updates (see CMS-001)
wp config get WP_DEBUG ; wp config get WP_DEBUG_DISPLAY
stat -c '%a %U:%G %n' wp-config.php              # last digit should be 0
for k in AUTH_KEY SECURE_AUTH_KEY LOGGED_IN_KEY NONCE_KEY AUTH_SALT SECURE_AUTH_SALT LOGGED_IN_SALT NONCE_SALT; do
  wp config get $k | grep -c 'put your unique phrase here' | sed "s/^/$k placeholder matches: /"
done
for f in wp-config.php wp-config.php.bak wp-config.php.old wp-config.php~ wp-config.bak wp-config.txt .wp-config.php.swp wp-content/debug.log .env .git/config; do
  curl -s -o /dev/null -w "%{http_code} $f\n" "https://example.com/$f"
done
```
A healthy `wp-config.php` request returns 200 with an empty body (PHP ran) or 403 or 404; it must never return PHP source. Anything other than 404 or 403 for the backup, log and `.env` names deserves a look at the body. Also confirm all eight keys exist and differ from each other, without printing them into shared logs.

## Pass criteria
- `DISALLOW_FILE_EDIT` is true (the same as removing the `edit_themes`, `edit_plugins` and `edit_files` capabilities from everyone).
- `wp-config.php` is readable only by the site owner and the web server user (the handbook suggests mode 400 or 440; 600 also meets this), is not world-readable, and, if possible, sits one level above the web root.
- All eight keys and salts are present, unique to this site, and none is the sample text.
- `WP_DEBUG_DISPLAY` is false in production, and no `debug.log`, backup copy of the config, `.env` or `.git` directory is reachable over the web.
- Config backups and other files with passwords are not stored in the web root.

## Fix
Add `define( 'DISALLOW_FILE_EDIT', true );` above the "stop editing" comment in `wp-config.php`. Fix permissions with `chmod 440 wp-config.php` (owner and group as appropriate for your PHP user). Generate new keys with `wp config shuffle-salts` (or paste a fresh set from the WordPress.org generator). Turn off display of errors with `define( 'WP_DEBUG_DISPLAY', false );`. Delete leftover copies and move any needed log outside the web root or deny it in the server config. On Apache you can add a `<Files "wp-config.php"> Require all denied </Files>` block to `.htaccess`; on nginx return 403 for that location.

## Risk and rollback
With `DISALLOW_FILE_EDIT` on, nobody can fix a broken plugin from the dashboard; use SFTP or Git instead. Rotating the keys logs every user out (including you) and ends all current sessions, which is also what you want after a suspected compromise. Too strict a mode (400 with a different owner than the PHP user) can make the site show an installation error; set it back to 640 to recover, then correct ownership. Rollback: remove the constant or restore the previous `wp-config.php` copy.
