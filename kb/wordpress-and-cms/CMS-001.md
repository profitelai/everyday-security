# CMS-001 · WordPress core, plugins and themes are current, and updates are applied automatically or on a short schedule

## Why it matters
Most hacked WordPress sites are not targeted individually. Automated scanners look for a known flaw in an outdated plugin or theme and exploit whatever answers. The fix for these flaws is almost always already published, so the gap is the time between release and installation. The WordPress project officially supports only the latest release and backports security fixes to older branches as a courtesy, so a site that sits on an old branch is depending on goodwill. Public lists of exploited vulnerabilities, such as the CISA catalogue, show that old flaws stay in active use for years.

## How to test
Run from the WordPress directory as the site owner (add `--path=/var/www/example` if elsewhere).
```bash
wp core version
wp core check-update
wp plugin list --fields=name,status,version,update,update_version,auto_update
wp theme list --fields=name,status,version,update
wp config get WP_AUTO_UPDATE_CORE      # error "not defined" means the default (minor releases only)
wp config get DISALLOW_FILE_MODS       # if true, the dashboard cannot install or update anything
wp config get DISABLE_WP_CRON          # if true, a system cron job must call wp-cron.php or `wp cron event run --due-now`
wp cron event list --fields=hook,next_run_relative | grep -E 'wp_version_check|wp_update_plugins|wp_update_themes|wp_maybe_auto_update'
wp eval 'echo PHP_VERSION, "\n";'
```
Compare the PHP version with the branches that still receive security fixes on the PHP supported-versions page. If you do not have shell access, the same information is on Dashboard, Updates, and under Plugins with the Automatic updates column.

## Pass criteria
- Core is on the newest release of a supported branch (`wp core check-update` prints nothing newer).
- No plugin or theme shows `update` as `available` for longer than your stated window (suggested: security updates within 7 days, the rest within 30). Written down, even as one line.
- Automatic updates are on for core minor releases (the default) and for plugins and themes you are comfortable updating unattended; the rest are updated by a named person on a calendar reminder.
- If `DISABLE_WP_CRON` or `DISALLOW_FILE_MODS` is true, there is another working update mechanism (system cron, managed host, deployment pipeline) and someone has confirmed it runs.
- PHP is a branch that still receives security fixes.
- Larger changes (major WordPress releases, big page-builder or e-commerce plugin updates) are tried on a staging copy first, or at minimum after a fresh backup (see CMS-009).

## Fix
Turn on auto-updates per plugin and theme from Dashboard, Plugins, Enable auto-updates, or with `wp plugin auto-updates enable --all` (WP-CLI 2.5.0 or later). For core, leave `WP_AUTO_UPDATE_CORE` undefined or set to `'minor'`; set it to `true` only if you accept unattended major upgrades. Install an update-notification email for the site administrator address so failures are noticed. Update the rest with `wp core update`, `wp plugin update --all` and `wp theme update --all` after taking a backup. Retire plugins that have been abandoned rather than leaving them on a stale version (CMS-002).

## Risk and rollback
An update can break a theme or plugin, and a failed automatic update can leave the site in maintenance mode (delete `.maintenance` in the site root). Auto-updating everything is a trade: a short outage risk versus a long exposure window; most small sites are better off with automatic updates plus a backup and an uptime monitor. Rollback: restore the pre-update backup (CMS-009), or reinstall the previous plugin version with `wp plugin install NAME --version=X.Y.Z --force`, and then switch that plugin's auto-updates off until the cause is understood.
