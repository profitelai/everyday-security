# CMS-008 · The whole site is served over HTTPS with WordPress configured to match, and security headers are set

## Why it matters
Without HTTPS, anyone on the same network can read or change what visitors and staff send, including the administrator login. WordPress builds its links from two stored addresses, so a site that has a certificate but still stores `http://` addresses produces mixed content, broken padlocks and redirect loops. Browser security headers are cheap protection against clickjacking, content sniffing and forced downgrades, and are normally added at the web server because WordPress itself sends only a few.

## How to test
```bash
wp option get siteurl ; wp option get home                      # both should start with https://
wp config get FORCE_SSL_ADMIN                                    # expect 1 or true
curl -sI http://example.com/ | sed -n '1p;/^[Ll]ocation/p'       # expect a 301 to https://
curl -sI http://example.com/wp-login.php | sed -n '1p;/^[Ll]ocation/p'
curl -sI https://example.com/ | grep -iE '^(strict-transport-security|x-content-type-options|x-frame-options|content-security-policy|referrer-policy|permissions-policy|x-powered-by|server):'
curl -sI https://example.com/wp-login.php | grep -iE '^(x-frame-options|content-security-policy|cache-control):'
curl -s https://example.com/ | grep -Eo "(src|href)=[\"']http://[^\"']+" | sort -u | head   # mixed content
wp search-replace 'http://example.com' 'https://example.com' --dry-run --skip-columns=guid   # shows how many stored http links remain
```
Also check the certificate is valid and not close to expiry (see the TLS pillar).

## Pass criteria
- Both stored addresses (`siteurl`, `home`) use `https://`, every `http://` request is redirected once to the matching `https://` address, and `FORCE_SSL_ADMIN` is true.
- Pages, images, scripts and stylesheets load over HTTPS only; no mixed content is reported.
- The HTTPS response carries `Strict-Transport-Security` (start with a short `max-age`, raise it once everything works), `X-Content-Type-Options: nosniff`, a clickjacking control (`X-Frame-Options` or CSP `frame-ancestors`), and `Referrer-Policy`. A full Content-Security-Policy is a bonus, not a requirement, for a WordPress site.
- The `X-Powered-By` header is not present, and the `Server` header does not carry an exact version.

## Fix
In Settings, General, set the WordPress Address and Site Address to `https://` (or `wp option update home 'https://example.com'` and the same for `siteurl`), add `define( 'FORCE_SSL_ADMIN', true );` to `wp-config.php`, and redirect HTTP to HTTPS in the web server. Repair stored links with `wp search-replace` (dry run first, always with a backup). Add the headers in the server config or with `Header always set ...` under Apache `mod_headers`, or `add_header ... always;` in nginx. Make sure cookies marked Secure and the proxy headers are right if a CDN or load balancer terminates TLS.

## Risk and rollback
Switching addresses with the wrong values can lock you out of the dashboard; keep a backup and know how to set the two options in the database or with WP-CLI. A Content-Security-Policy often breaks page builders, analytics and the admin area, so introduce it in report-only mode on the public pages first. HSTS is sticky: a long `max-age` or `includeSubDomains` before every subdomain works over HTTPS can cause outages that cannot be undone quickly. Rollback: remove the headers, restore the two options, and reload the server.
