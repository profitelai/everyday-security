# CMS-004 · Login attempts to wp-login.php are rate limited so password guessing is slowed or blocked

## Why it matters
Every WordPress site has the same login address, so bots try common passwords and passwords leaked from other sites against it all day. The WordPress documentation lists rate limiting at the web server, CDN or firewall as a primary defence, because requests that are stopped before PHP starts cost the server almost nothing. Without it, a guessing run can both succeed and slow your site to a crawl.

## How to test
Only against your own site, from a machine you can afford to have blocked for a while. This sends 30 failed logins for a user that does not exist.
```bash
for i in $(seq 1 30); do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST \
    --data-urlencode "log=cms-test-nosuchuser" --data-urlencode "pwd=wrong-$i" \
    https://example.com/wp-login.php
done | sort | uniq -c
```
A normal failed login returns 200 (the form again). Watch for 403, 429, a CAPTCHA page, or a drop in speed. Repeat with `https://example.com/xmlrpc.php` if XML-RPC is enabled (see CMS-005). Then read the server configuration.
```bash
sudo nginx -T 2>/dev/null | grep -nE 'limit_req(_zone)?|wp-login|xmlrpc'
sudo fail2ban-client status        # look for a jail that watches the web access log for wp-login
```

## Pass criteria
A burst of failed logins from one address gets throttled or blocked within a handful of attempts, either at the web server (`limit_req` on `/wp-login.php`), a firewall or CDN rule, a fail2ban jail, or a login-limiting plugin. The limit does not lock the real account for everyone (it is per client address, not a hard account lockout an attacker can trigger against your owner). Login pages are served only over HTTPS. Failed logins are logged somewhere someone can read them.

## Fix
At nginx, define a zone and apply it to the login location, for example `limit_req_zone $binary_remote_addr zone=wplogin:10m rate=10r/m;` and `location = /wp-login.php { limit_req zone=wplogin burst=5 nodelay; ... }`, keeping the normal PHP handling inside that block. Alternatively add a fail2ban jail with a filter on POSTs to `wp-login.php`, or use the rate-limiting or bot rules of your CDN or host. A CAPTCHA or Turnstile-style challenge on the login form helps against bots, and a second factor (CMS-003) protects you even when guessing succeeds. If the site sits behind a CDN or reverse proxy, make sure the web server sees the real visitor address, otherwise you will rate-limit the proxy and block everybody.

## Risk and rollback
Too strict a limit can lock out staff who mistype passwords, or whole offices sharing one public address; start permissive and tighten after watching logs. Never apply the limit to `/wp-admin/admin-ajax.php`, which the public site often uses. Rollback: remove the `limit_req` line or unban an address with `fail2ban-client set JAIL unbanip ADDRESS`, then reload nginx.
