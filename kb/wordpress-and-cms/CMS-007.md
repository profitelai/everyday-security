# CMS-007 · File permissions are tight, and PHP files cannot be executed from the uploads folder

## Why it matters
If the account that runs PHP can write to the WordPress program files, any bug in any plugin lets an attacker plant or alter code in place. The uploads folder has to be writable, so it is where attackers drop a web shell after abusing an upload flaw; if the server will execute PHP found there, one such file hands over the site. Locking down write access and refusing to run scripts from uploads limits what a single vulnerable plugin can do.

## How to test
Run on the server in the WordPress directory.
```bash
cd /var/www/example
stat -c '%a %U:%G %n' . wp-config.php wp-admin wp-includes wp-content wp-content/plugins wp-content/themes wp-content/uploads
ps -eo user,comm | grep -E 'php-fpm|apache2|httpd|nginx' | sort -u   # which user runs PHP
find . -perm -o+w \( -type f -o -type d \) -not -type l | head -20   # anything world-writable
find wp-admin wp-includes -writable -type f | head                   # run as the PHP user (sudo -u USER ...) to see if it can write core
find wp-content/uploads -type f \( -iname '*.php' -o -iname '*.phtml' -o -iname '*.phar' -o -iname '*.php[0-9]' -o -iname '.htaccess' \) -print
```
Then prove PHP does not run from uploads. Create a harmless probe and request it, then delete it.
```bash
echo '<?php echo 6*7;' | sudo tee wp-content/uploads/cms-exec-test.php >/dev/null
curl -s -o - -w "\nHTTP %{http_code}\n" https://example.com/wp-content/uploads/cms-exec-test.php
sudo rm wp-content/uploads/cms-exec-test.php
```

## Pass criteria
- Nothing is world-writable (no `777`, `666` or `o+w`); directories are typically 755 and files 644, and `wp-config.php` is tighter (CMS-006).
- The PHP runtime user cannot write to `wp-admin`, `wp-includes` or the plugin and theme folders, other than during a controlled update window (see Risk). Only `wp-content/uploads` and any cache directory the site truly needs are writable by it.
- No PHP files sit in `wp-content/uploads`.
- The probe request returns 403 or 404, or shows the raw text rather than `42`. If the response is `42`, the folder executes PHP and the check fails.

## Fix
Own the files by a deploy or site-owner user and give PHP's user only group write on the folders it needs. Reset modes with `find . -type d -exec chmod 755 {} \;` and `find . -type f -exec chmod 644 {} \;`, then tighten `wp-config.php`. Stop PHP running from uploads. nginx: put `location ~* ^/wp-content/uploads/.*\.(php|phtml|phar)$ { return 403; }` before the general PHP handler. Apache: in the uploads folder, a `<FilesMatch "\.(php|phtml|phar)$"> Require all denied </FilesMatch>` block (this needs `AllowOverride` to permit it in `.htaccess`, or put it in the virtual host). Remove any PHP file found in uploads after checking it is not legitimate.

## Risk and rollback
When PHP cannot write core and plugin folders, the dashboard cannot install or auto-update them; run updates through WP-CLI as the owner user, a deployment pipeline or a managed host (CMS-001), or loosen group write only during update windows. Some plugins write cache or log files into `wp-content`; check the plugin's documentation before locking that folder. A few themes and plugins legitimately keep PHP in uploads; test before blocking. Rollback: restore the previous modes from a `getfacl` or `stat` listing taken beforehand, and remove the `location` block.
