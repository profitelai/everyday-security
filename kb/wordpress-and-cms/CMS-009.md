# CMS-009 · Backups cover both files and database, are kept off the server, and a restore has been tested on a staging copy

## Why it matters
A WordPress site is two things that must match: the files (core, plugins, themes, uploads, `wp-config.php`) and the database (all pages, orders, users, settings). A backup of one without the other is usually not a working site. Backups that live only on the same server are lost to the same hack, deletion or disk failure, and a backup that has never been restored is a hope, not a recovery plan. A copy restored to a staging site is also the safest place to try updates before they touch the live site (CMS-001).

## How to test
Ask for the schedule, the storage location and the last restore date, then check them.
```bash
crontab -l ; sudo crontab -l ; systemctl list-timers --no-pager | grep -i backup   # what runs and when
ls -lh /path/to/backups | tail                                                    # newest archive, size, age
tar -tzf /path/to/backups/latest-files.tar.gz | grep -E 'wp-config.php|wp-content/uploads' | head -3
head -c 400 /path/to/backups/latest-db.sql                                        # real dump header, not an empty file
wp db export - | tail -n 5                                                         # proves the dump command works now
for p in backup.zip backup.sql site.tar.gz wp-content/backup-db/ wp-content/ai1wm-backups/ wp-content/updraft/; do
  curl -s -o /dev/null -w "%{http_code} $p\n" "https://example.com/$p"
done
```
Then do a real restore drill on a separate host or local container: unpack the files, create an empty database, run `wp db import latest-db.sql`, edit the database settings in `wp-config.php`, run `wp search-replace 'https://example.com' 'https://staging.example.test' --skip-columns=guid`, then `wp core verify-checksums` and click through the home page, the login and the key forms or the checkout.

## Pass criteria
- Automatic backups include the database and all files that cannot be rebuilt from the vendor (uploads, `wp-config.php`, custom theme code, premium plugin files).
- Frequency matches how often the content changes (the handbook suggests weekly for small sites and daily for busy ones; daily is a good default); e-commerce or booking sites need the database more often.
- At least one copy is stored somewhere an attacker on the web server cannot delete or encrypt (a different account, immutable or versioned storage, or an offline copy), and the copies are encrypted, since they contain database passwords and customer data.
- Several generations are kept, not only the latest.
- Backup files are not reachable by URL (every probe above returns 403 or 404).
- A full restore to a clean site has been completed within the last 6 months, with the time it took and the steps written down.

## Fix
Use the host's snapshot service plus a second independent backup (a maintained backup plugin writing to remote storage, or `wp db export` and an archive of the site folder pushed by a scheduled job to object storage or another server). Keep backups outside the web root, protect the credentials of the remote storage with write-only or restricted rights, and add a restore drill to the calendar. Keep a short runbook: where backups are, who can restore, how to point DNS.

## Risk and rollback
A database export under load can slow the site; run it at a quiet hour (and, for InnoDB tables, WP-CLI passes options such as `--single-transaction` through to the dump tool). Never import a dump into the live database to "test"; always use a separate database. Restoring to staging copies live customer data, so protect staging with a password, block search engines, and stop it sending real emails. Rollback: backup jobs can be disabled by removing the cron entry or timer; keep the previous schedule documented.
