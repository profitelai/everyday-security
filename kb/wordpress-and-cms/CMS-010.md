# CMS-010 · WordPress core and plugin files are checked against official checksums on a schedule, and unexpected files are investigated

## Why it matters
A compromised WordPress site often looks normal: pages load, but a modified core file, an extra PHP file in a plugin folder or a hidden administrator quietly sends spam, redirects visitors or keeps a way back in. WordPress.org publishes checksums for every core release and for plugins in its directory, so you can check that your installed files match the originals without any commercial scanner. Doing this regularly turns "we noticed after Google flagged us" into "we noticed the same day".

## How to test
Run as the site owner from the WordPress directory.
```bash
wp core verify-checksums
wp core verify-checksums --include-root              # also warns about unknown files in the web root
wp plugin verify-checksums --all
wp plugin list --status=must-use,dropin --fields=name,status
find wp-content -type f -name '*.php' -mtime -7 -not -path '*/cache/*' | head -50   # recently changed PHP
find wp-content/uploads -type f \( -iname '*.php*' -o -iname '*.phtml' -o -iname '*.phar' \)
grep -rIlE 'eval\(\s*(base64_decode|gzinflate|str_rot13)' wp-content | head          # crude pattern search, expect false positives
wp user list --role=administrator --fields=ID,user_login,user_registered
wp cron event list --fields=hook,next_run_relative | head -40                          # unfamiliar hooks
```
The core command prints `Success: WordPress installation verifies against checksums.` when all is well, and warnings such as `File doesn't verify against checksum` or `File should not exist` otherwise. The plugin command only covers plugins hosted on WordPress.org; premium and custom plugins need a comparison with the vendor's download or your own Git repository.

## Pass criteria
- `wp core verify-checksums` succeeds, or each warning has a written explanation (for example a deliberate hosting-provider file).
- `wp plugin verify-checksums --all` passes for directory-hosted plugins, apart from harmless documentation differences; premium or custom plugins are verified by another named method.
- No PHP files in uploads, no unexplained must-use plugins or drop-ins, no unknown administrators or scheduled tasks.
- A job runs these commands on a schedule (at least weekly) and sends the output to a mailbox that someone reads, or to a monitoring system, and the last 30 days of results are available.

## Fix
Create a small script that runs the checks above and a cron job or systemd timer to run it daily, mailing output only when it is not clean. Restore any altered core file with `wp core download --force --skip-content` (this overwrites core files but keeps `wp-content`) and reinstall a modified plugin from a clean copy. If you find a file you cannot explain, treat the site as compromised: take a forensic copy, restore from a clean backup (CMS-009), update everything (CMS-001), rotate the keys and all passwords (CMS-006, CMS-003), and look for the cause before putting the site back. Add file-change monitoring or a server-side scanner if the site is business critical.

## Risk and rollback
The checks only read files, so they are safe; the grep search can be slow on very large sites. A `--force` core download overwrites any local edits to core files, which should not exist but sometimes do on older sites; note them first. Content in `wp-content` is not touched by that command. Rollback: restore the replaced files from the pre-repair copy you took.
