# IR-008 · Recovery is done from known-good sources with credentials rotated, and every incident ends with a written review and tracked actions

## Why it matters
Restoring service is not the end. If you bring a system back from a backup that already contains the attacker's foothold, or leave the stolen password valid, the attacker returns. Equally, an incident that is never reviewed teaches nothing, and the same weakness is exploited again. The lifecycle guidance treats eradication, recovery and post-incident learning as distinct steps: find and remove the root cause, restore and validate systems, then record what to change in policies, training and controls.

## How to test
1. Ask for the last incident or near-miss record and its review. If none has happened, ask how a review would be run and by whom.
2. Check that the plan's recovery section requires: a clean build or restore from a backup taken before the earliest known compromise; patching the entry point before reconnecting; rotating every credential, API key, token and certificate that was on or reachable from the system; checking for persistence (new users, SSH keys, cron jobs, web shells, mailbox forwarding rules, OAuth app grants); validating the system before it returns to service; and watching it closely for a defined period afterwards.
3. Check that the backups can actually be restored and that the backup copy cannot be altered by whoever controls the server (see BAK-004 and BAK-008 for backup tests and immutability).
4. Read the review template. It should capture a timeline, root cause, what worked and what did not, data affected, time to detect and to contain, and a list of actions each with an owner and a date.
5. Pick two past actions and confirm they were completed or consciously dropped.

## Pass criteria
A written recovery procedure with the steps above exists; recovery sources are known-good and tested; credential rotation is mandatory; a blameless review is held within a set number of days of closure (two weeks is a common target) and recorded; actions are tracked to completion; the plan and training are updated from the findings.

## Fix
Add a "recovery and closure" page to the plan with a checklist and a one-page review template. Schedule the review before the incident closes. Keep a running action list in the same tracker you use for other work. Where the root cause cannot be proven, rebuild rather than clean in place.

## Risk and rollback
Rebuilding takes longer than cleaning and may lose recent data; weigh this against the risk of a hidden foothold, and record the decision. Restoring an old backup can lose transactions made after it; reconcile with customers if needed. Rollback: keep the pre-recovery snapshot of the compromised system until the lead releases it, so you can return to it if the rebuild fails.
