# DNS-001 · Registrar and DNS-provider accounts use MFA and send change alerts

## Why it matters
Whoever controls the registrar or DNS-host login controls where the domain's web traffic and mail go, and can request certificates for it. A stolen password on one of these accounts is a full takeover of the domain's identity, so these logins deserve stronger protection than almost any other account.

## How to test
No command can see inside the account; review it by hand.
1. List every login that can change the domain at the registrar and at the DNS host (they may be the same company). Remove people who no longer need access.
2. For each login, confirm in the security settings that multi-factor authentication is enabled. Note whether it is a security key or passkey, an authenticator app, or SMS.
3. Confirm the account recovery email and phone are controlled by you, and that the recovery mailbox is not on the domain itself (otherwise losing the domain also loses the way back in).
4. Check that notifications are turned on for DNS record changes, nameserver or contact changes, transfer requests, and sign-ins from new devices. Make a harmless test change and see whether an alert arrives.
5. Check that any API tokens are scoped to the zones they need and are not stored in shared documents.

## Pass criteria
Every user has MFA enabled (security key, passkey or authenticator app preferred over SMS), logins are per person rather than shared, recovery contacts are independent of the domain, and at least one alert channel reaches a monitored mailbox when records or contacts change. If the provider has no change alerts, a scheduled zone export that is compared against the last copy is acceptable.

## Fix
Enable MFA for all users, preferring phishing-resistant methods where the provider supports them. Store recovery codes in a password manager and keep at least two people able to administer the account. Turn on every security notification the provider offers and point it at a group mailbox. Replace broad API tokens with narrowly scoped ones.

## Risk and rollback
The main risk is locking yourself out: keep recovery codes and a second administrator before enforcing MFA, and test sign-in in a private window afterwards. If a method proves unusable, add another factor first and only then remove the old one.
