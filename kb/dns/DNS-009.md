# DNS-009 · Public DNS does not expose internal hostnames or private addresses

## Why it matters
Anyone can query your public zone, so a record such as `db-prod` or `vpn-admin` resolving to a private address tells outsiders what exists inside your network and how it is laid out. Private address ranges (RFC 1918) are only meaningful inside your network, so such a record has no legitimate use for the public. Names used on publicly trusted certificates are also visible in public certificate logs, so the same care applies there.

## How to test
Export the zone into `names.txt`, one hostname per line.
```bash
while read -r h; do
  dig +short A "$h" | grep -E '^(10\.|127\.|192\.168\.|172\.(1[6-9]|2[0-9]|3[01])\.)' | sed "s/^/$h /"
done < names.txt
```
Also read the name list for hosts that describe internal systems (databases, admin panels, build servers, VPN gateways).

## Pass criteria
No public record resolves to a private, loopback or link-local address unless it is a documented exception, and no name in the public zone describes an internal-only system.

## Fix
Move internal names into a separate internal zone served only by your internal resolvers (split-horizon), or into a private domain. Delete the public records, and prefer neutral hostnames for anything that must be public.

## Risk and rollback
Staff or software that resolves these names through public DNS will stop finding them, so first confirm the internal resolver serves the same names. Rollback: re-add the record from the zone export you took before the change.
