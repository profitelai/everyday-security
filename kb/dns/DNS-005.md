# DNS-005 · DNSSEC is enabled where the registrar and DNS host support it, and validates

## Why it matters
DNSSEC lets a validating resolver check that an answer was signed by the zone's owner, which protects against forged or tampered DNS responses. It only works end to end when the zone is signed and the parent zone holds a matching DS record. A half-finished setup is worse than none: a DS record that does not match the signing keys makes validating resolvers return errors, and the domain appears to be down for a large share of users.

## How to test
```bash
dig +short DS example.com
dig +short DNSKEY example.com
dig +noall +comments example.com A @1.1.1.1 | grep -E 'flags|status'
dig +cd +noall +comments example.com A @1.1.1.1 | grep status
```
A signed domain has DS and DNSKEY records, and the validating resolver's reply carries the `ad` flag. If the normal query returns `SERVFAIL` but the `+cd` query (validation switched off) returns `NOERROR`, the DNSSEC chain is broken.

## Pass criteria
Either the zone is signed, the DS at the parent matches a published key, and validation succeeds, or there is no DS at all and the lack of DNSSEC is a recorded decision because the registrar or DNS host does not support it. A DS with no matching signed zone is a failure.

## Fix
Enable signing at the DNS host, then copy the DS data it shows into the registrar's DNSSEC settings. Prefer a host that rolls keys automatically (operational practices are in RFC 6781). Before moving DNS to another provider, plan the DS record: remove it, wait for its TTL to pass, and add a new one only after the new provider signs the zone.

## Risk and rollback
Mistakes take the domain offline for validating resolvers, so change DS records only with the key material in hand and re-run the test right after. Rollback: delete the DS record at the registrar; the zone then resolves unsigned once cached DS answers expire.
