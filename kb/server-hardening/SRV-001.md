# SRV-001 · SSH login policy is a deliberate, documented decision with compensating controls

## Why it matters
SSH is the administrative front door, and any public address is probed for it all day. Key-only logins and no direct root login remove the easiest attacks. Many small-business owners still keep password login or root login on purpose, for convenience or as a recovery path. That is a legitimate trade-off only if it is a written decision with compensation (see "Pass criteria"), not an unexamined default.

## How to test
```bash
sudo sshd -T | grep -Ei '^(permitrootlogin|passwordauthentication|kbdinteractiveauthentication|pubkeyauthentication|permitemptypasswords|maxauthtries|logingracetime|allowusers|allowgroups|clientaliveinterval|clientalivecountmax) '
ls -l /etc/ssh/sshd_config.d/ 2>/dev/null
ssh -V
# fingerprints of every key that can log in as a user (look for people who left):
sudo ssh-keygen -lf /home/USER/.ssh/authorized_keys
```
From a second computer, check what the server really offers: `ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password,keyboard-interactive USER@SERVER_IP`. A password prompt means password login is on. Use `sshd -T`, not the config file, because drop-in files and the first-value-wins rule change what applies.

## Pass criteria
Either (a) `passwordauthentication no`, `kbdinteractiveauthentication no`, and `permitrootlogin` is `no` or `prohibit-password`; or (b) password and/or root login is kept deliberately, with a dated note saying who needs it and why, plus compensation: a long unique password or passphrase, an active brute-force jail (SRV-006), and either a firewall or `AllowUsers` restriction to known addresses or a VPN. In both cases `permitemptypasswords no`, a named `AllowUsers` or `AllowGroups` list, a modest `maxauthtries`, a short `logingracetime`, and no stale entries in `authorized_keys`. Modern OpenSSH has no `Protocol` option because SSH-1 support was removed years ago; a very old version in `ssh -V` is worth flagging separately.

## Fix
Put changes in a drop-in such as `/etc/ssh/sshd_config.d/10-hardening.conf` (on current Debian and Ubuntu the main file includes that directory first, and the first value found wins, so keep the name sorting before cloud-image files). Example: `PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `PermitRootLogin prohibit-password`, `MaxAuthTries 4`, `LoginGraceTime 30`, `AllowUsers deploy admin`, `ClientAliveInterval 300`, `ClientAliveCountMax 2`. Note that the ClientAlive pair drops unresponsive connections; it does not log out an idle but connected user. Install and prove your own key first (`ssh-copy-id`), validate with `sudo sshd -t`, then `sudo systemctl reload ssh` (`sshd` on RHEL-family systems).

## Risk and rollback
A wrong change locks you out of the server. Keep one logged-in session open and prove a fresh login from a second terminal before closing either. Schedule an automatic revert before you reload: `sudo systemd-run --on-active=10m --unit=ssh-revert /bin/sh -c 'rm -f /etc/ssh/sshd_config.d/10-hardening.conf; systemctl reload ssh'`, then cancel it with `sudo systemctl stop ssh-revert.timer` once the new login works. Make sure `AllowUsers` includes the account you are using, and confirm you have provider console or rescue access.
