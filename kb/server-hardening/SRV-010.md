# SRV-010 · The clock is synchronized and logs are rotated, bounded and retained deliberately

## Why it matters
Logs are how you learn what happened after an incident, but only if they exist, line up in time and have not filled the disk. A drifting clock breaks event correlation across servers and can cause TLS, DKIM and two-factor-code failures. Unbounded logs, especially Docker's default JSON logs and a huge journal, are a classic cause of a full disk that takes websites and mail down.

## How to test
```bash
timedatectl status | grep -Ei 'time zone|synchronized|NTP'
chronyc tracking 2>/dev/null | head -5
df -h / /var /var/log; df -i /
journalctl --disk-usage
sudo du -xh --max-depth=1 /var/log | sort -h | tail -8
sudo logrotate -d /etc/logrotate.conf 2>&1 | tail -15
docker info --format '{{.LoggingDriver}}'; cat /etc/docker/daemon.json 2>/dev/null
```
`logrotate -d` is a dry run and changes nothing.

## Pass criteria
`timedatectl` reports the system clock as synchronized with an active NTP service (chrony or systemd-timesyncd). Web, mail and application logs rotate by size or age with compression, and the retention period is a written decision that fits your investigations and privacy obligations (client IP addresses are personal data in some jurisdictions). The journal has a size cap (`SystemMaxUse=`). Docker's `json-file` driver has `max-size` and `max-file` set, because by default its logs are not size-limited. No filesystem is above about 80% in blocks or inodes.

## Fix
Enable time sync with `sudo timedatectl set-ntp true` or install `chrony`. Add logrotate stanzas in `/etc/logrotate.d/` for application logs, with a `postrotate` that makes the program reopen its file (for nginx, `nginx -s reopen` or a USR1 signal). Cap the journal with `SystemMaxUse=1G` in a drop-in under `/etc/systemd/journald.conf.d/`. For Docker set `"log-driver": "json-file"` with `"log-opts": {"max-size": "10m", "max-file": "3"}` in `daemon.json`, and restart the daemon.

## Risk and rollback
Shorter retention shrinks the window in which an old intrusion can be investigated; ship important logs off the server if you can. Vacuuming the journal deletes data irreversibly. Docker log limits apply to containers created after the change, so recreate them. A step in the clock can disturb running applications. Rollback: remove the logrotate stanza or the drop-in and reload the service; logs already deleted are gone, so size limits conservatively.
