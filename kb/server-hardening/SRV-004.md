# SRV-004 · Docker published ports are controlled and do not silently bypass the host firewall

## Why it matters
When a container publishes a port, Docker adds its own firewall rules, and the traffic is diverted before it reaches the chains that ufw manages. Docker's documentation says plainly that Docker and ufw are incompatible in this respect. A ufw rule that looks like "only port 443 is open" therefore says nothing about a database container published as `5432:5432`, which is reachable on every host address by default.

## How to test
```bash
docker ps --format 'table {{.Names}}\t{{.Ports}}'
sudo iptables -S DOCKER-USER      # empty chain is normal; nftables hosts: sudo nft list ruleset
docker version --format '{{.Server.Version}}'
```
In the Ports column, `0.0.0.0:PORT->` or `[::]:PORT->` is published to every interface; `127.0.0.1:PORT->` is local only; a bare `80/tcp` is not published at all. From another computer, against your own server only, confirm reality: `nmap -Pn -p PORT SERVER_IP`.

## Pass criteria
Each published port is either bound to `127.0.0.1` (and reached through nginx or Apache on the host) or intentionally public and also listed in your port inventory (SRV-002). Databases, caches and queues publish no ports; they are reached over a private Docker network by service name. Any further restriction of container traffic is placed in the `DOCKER-USER` chain, not in ufw.

## Fix
In Compose, write `ports: ["127.0.0.1:8080:80"]` instead of `"8080:80"`, or remove `ports:` for backends. To make loopback the default for the default bridge network, set `"ip": "127.0.0.1"` in `/etc/docker/daemon.json`; for user-defined networks the documented option is `com.docker.network.bridge.host_binding_ipv4`. For source-address limits use `DOCKER-USER`; rules there see the container's address after address translation, so match on the original destination port with a conntrack match, as Docker's own page shows. Do not switch off Docker's firewall management (`iptables: false`); the documentation warns it breaks container networking.

## Risk and rollback
Binding to loopback cuts off anything that reached the container from other hosts, so list those clients first. Changing `daemon.json` needs a daemon restart, which stops containers unless `live-restore` is enabled; do it in a quiet period. A bad `DOCKER-USER` rule can block all container traffic, so apply it with a scheduled revert (`sudo systemd-run --on-active=10m ...`) and keep a second SSH session. Rollback: restore the previous Compose file and run `docker compose up -d`, or remove the rule.
