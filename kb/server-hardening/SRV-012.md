# SRV-012 · Alerts for outages, full disks and failed jobs reach a person who actually reads them

## Why it matters
Most hardening decays without anyone noticing: a certificate expires, a backup job fails for weeks, a disk fills, a service crash-loops, a failed update sits unapplied. An alert that goes to an unread mailbox, or to the same server that just died, is the same as no alert.

## How to test
```bash
systemctl --failed --no-pager
systemctl list-timers --all --no-pager | head -30
grep -rs '^MAILTO' /etc/crontab /etc/cron.d; sudo crontab -l
df --output=pcent,target -x tmpfs -x devtmpfs | sort -rn | head -5
ls /var/run/reboot-required 2>/dev/null
sudo mailq | tail -3
```
Then walk the list in "Pass criteria" and ask, for each item, which tool raises the alert, where it is delivered and who acts on it. Run a harmless drill: send a test message through the same channel the real alerts use and time how long it takes someone to see and acknowledge it.

## Pass criteria
For each of these there is an alert with a named recipient: site and HTTPS reachable (checked from outside the server), certificate expiry, disk and inode usage above a threshold (for example 85%), failed systemd units, failed or missing backup runs, a pending reboot beyond its window, and a growing mail queue on a mail host. At least one check runs from a different machine or an external service. Alerts go to more than one person or channel, are tuned so that they are rare enough to be taken seriously, and a drill was acknowledged in the last quarter.

## Fix
Start small. Use an external uptime monitor for the public URLs. On the server, add a disk check run by cron or a systemd timer, for example:
```bash
#!/bin/sh
# /usr/local/bin/disk-alert.sh
LIMIT=85
df --output=pcent,target -x tmpfs -x devtmpfs | tail -n +2 | while read p t; do
  [ "${p%\%}" -ge "$LIMIT" ] && echo "disk $t at $p on $(hostname)"
done
```
Cron mails any output to `MAILTO`, so set it to a mailbox that is read and make sure the server can deliver mail. Add `OnFailure=` handlers or a wrapper to scheduled jobs so failures send a message, and have backup scripts report both success and failure.

## Risk and rollback
Too many alerts teach people to ignore them; raise thresholds before adding more checks. Alert mail sent from the server itself fails when the server or its mail system is the thing that is broken, which is why an external check matters. Monitoring agents consume resources and, if they expose a port, widen attack surface (SRV-003). Rollback: remove the timer or cron entry.
