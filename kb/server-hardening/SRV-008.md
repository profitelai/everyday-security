# SRV-008 · Web roots, config files and keys have tight ownership and permissions, and no secrets sit in the web root

## Why it matters
Files served by the web server are one request away from the internet. A forgotten `.env`, database dump, `.git` directory or backup archive in the web root hands out credentials and source code; a file the web server user can write lets an attacker who finds any upload flaw plant code that runs. On shared servers, world-readable config files let one compromised site read another's database password.

## How to test
```bash
sudo find /var/www -xdev \( -type f -o -type d \) -perm -o+w -ls
sudo find /var/www -xdev \( -name '.env*' -o -name '.git' -o -name '*.sql' -o -name '*.sqlite*' -o -name '*.db' -o -name '*.bak' -o -name '*.old' -o -name '*.zip' -o -name '*.tar.gz' -o -name 'phpinfo.php' \) -ls
stat -c '%a %U:%G %n' /etc/shadow /etc/ssh/sshd_config /root/.ssh /etc/ssl/private
curl -s -o /dev/null -w '%{http_code}\n' https://example.com/.env
curl -s -o /dev/null -w '%{http_code}\n' https://example.com/.git/config
```
Adjust `/var/www` to your document roots. The `curl` probes only request your own site and should answer 404 or 403.

## Pass criteria
Nothing in the web roots is world-writable. Application code is owned by a deploy user or root, and the web server user can write only designated upload, cache and session directories. Files holding credentials are mode 640 or 600, owned by root or the application user, not readable by "other". Private keys are readable only by root and the service group that needs them. Databases (including SQLite files), dumps, backups and `.git` are outside any directory the web server serves, or blocked by the web server config. The probe URLs do not return 200.

## Fix
Record the current state first: `sudo find /var/www -xdev -printf '%m %u:%g %p\n' > /root/perms-before.txt`. Then set code to 644/755 owned by the deploy user, `chmod 640` and `chown root:www-data` on config files, and move databases and backups outside the docroot. Deny dot-files in nginx with `location ~ /\.(?!well-known) { deny all; }`, and restrict uploads to what the application requires. A SQLite database needs both the file and its directory writable by the application user only.

## Risk and rollback
Tightening permissions can break uploads, caches, sessions, cron jobs and deployment scripts that quietly relied on loose access. Change one site at a time and test its main functions. Rollback: reapply the modes and owners recorded in `/root/perms-before.txt`, scripting one `chmod` and one `chown` per line, and rehearse that on a copy before you rely on it in production.
