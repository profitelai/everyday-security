# SRV-007 · Services and containers run as unprivileged users with least privilege

## Why it matters
When a web application is exploited, the attacker inherits the identity of the process. A PHP or Node process running as root hands over the whole machine; one running as a dedicated user with no write access outside its own directories contains the damage to that application and its data.

## How to test
```bash
ps -eo user:15,pid,args --no-headers | grep -E 'nginx|apache2|php-fpm|node|gunicorn|mysqld|postgres|redis' | grep -v grep
grep -HE '^(user|group) *=' /etc/php/*/fpm/pool.d/*.conf
awk -F: '$3==0 {print $1}' /etc/passwd          # only root should be listed
getent group docker sudo                         # who is root-equivalent
systemd-analyze security --no-pager | head -30   # exposure score per service
docker ps -q | xargs -r docker inspect --format '{{.Name}} user={{.Config.User}} privileged={{.HostConfig.Privileged}}'
```
An empty `user=` means the container's main process runs as root inside the container.

## Pass criteria
Only the web server's master process runs as root (to bind ports 80 and 443); workers run as a service user. PHP-FPM pools use unprivileged users, ideally one per site. Node, Python and other application processes are systemd services with a dedicated `User=`. Databases run under their own accounts. Containers are not `privileged`, and where an image allows it they run with a non-root `USER`. The `docker` group, which is effectively root on the host, has only the people who need it. Services show a reasonable `systemd-analyze security` score for their role.

## Fix
Create a dedicated account (`sudo useradd --system --home /srv/app --shell /usr/sbin/nologin app`) and set `User=app` in the unit. Add sandboxing from `systemd.exec`: `NoNewPrivileges=yes`, `PrivateTmp=yes`, `ProtectHome=yes`, `ProtectSystem=strict` with `ReadWritePaths=` for the directories the app must write. For images, add a `USER` line to the Dockerfile or set `user:` in Compose. Set `user` and `group` in each PHP-FPM pool.

## Risk and rollback
Services fail with "permission denied" when they need a file or directory the new user cannot reach. `ProtectSystem=strict` also makes SQLite files and their `-wal` and `-shm` companions read-only unless their directory is listed in `ReadWritePaths=`. Test on staging or in a quiet period and watch `journalctl -u SERVICE`. Rollback: remove the drop-in (`systemctl edit --full` or the file in `/etc/systemd/system/SERVICE.service.d/`), run `sudo systemctl daemon-reload` and restart the unit.
