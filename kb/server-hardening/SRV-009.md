# SRV-009 · Secrets are kept out of repositories and dumps, and rotated after any exposure

## Why it matters
Passwords, API keys, tokens and private keys leak through repositories (including old commits), container configuration, shell history, `phpinfo()` pages, support tickets and screenshots. Deleting a leaked secret from a file does not undo the leak: anyone who copied it still has it. Only rotation makes an exposed secret harmless.

## How to test
Print names, never values, when reviewing:
```bash
git -C /path/to/repo ls-files | grep -Ei '(^|/)(\.env[^/]*|[^/]*\.pem|[^/]*\.key|id_rsa|credentials[^/]*)$'
git -C /path/to/repo log --all --oneline -S'BEGIN PRIVATE KEY' | head
git -C /path/to/repo log --all --oneline --diff-filter=A -- '.env' '*.env' | head
docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' CONTAINER | cut -d= -f1
systemctl show -p Environment SERVICE | tr ' ' '\n' | cut -d= -f1
grep -rIl 'phpinfo(' /var/www 2>/dev/null
grep -lE '(mysql|psql).*(-p[^ ]|--password)' ~/.bash_history
```
Then ask the people involved: has any secret ever been pasted in chat, email or a ticket, or shared with someone who has left?

## Pass criteria
No credential files are tracked in version control, and history searches find nothing, or the matching secrets were rotated. Secrets are read at run time from a file outside the web root with restrictive permissions (for example a systemd `EnvironmentFile=` with mode 600/640, or Docker/Compose secrets), or from a password manager or vault; they are not baked into images. Each environment has its own secrets. A short written procedure says how to rotate each key, who does it, and that it has been practised. No `phpinfo()` pages or debug endpoints remain.

## Fix
Move secrets out of code into the mechanisms above, add `.env` and key patterns to `.gitignore`, and add an automated secret scanner as a pre-commit or CI step. When something was exposed, rotate first, then clean up: create the new secret, deploy it, verify, revoke the old one. Rewriting git history is tidying, not remediation.

## Risk and rollback
Rotating breaks every system that still holds the old value (cron jobs, other servers, mobile apps, third-party integrations), so list consumers first and keep the old secret valid until the new one is verified, unless the old one is known to be compromised, in which case accept short breakage. Keep a break-glass copy of critical credentials in the password manager, not on the server.
