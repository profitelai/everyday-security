# SRV-011 · Installed packages, dependencies and container images are scanned for known vulnerabilities on a schedule

## Why it matters
Automatic OS updates (SRV-005) do not touch container images, application dependencies or software installed by hand. Those age silently: a six-month-old image is full of fixed-upstream flaws. A scheduled scan turns "I think we are patched" into a list with owners and dates.

## How to test
```bash
# operating-system packages on the host
sudo trivy rootfs --pkg-types os --scanners vuln --severity HIGH,CRITICAL /
# every local container image
docker images --format '{{.Repository}}:{{.Tag}}' | grep -v '<none>' | xargs -r -n1 trivy image --scanners vuln --severity HIGH,CRITICAL
# application dependencies (composer.lock, package-lock.json, ...)
trivy fs --scanners vuln --severity HIGH,CRITICAL /path/to/app
# Debian only, alternative for OS packages
debsecan --suite "$(. /etc/os-release; echo $VERSION_CODENAME)" --only-fixed
```
Then check whether a scheduled job exists: `systemctl list-timers --all | grep -i -E 'trivy|scan'`, `sudo crontab -l`.

## Pass criteria
A scan runs automatically at least weekly and its output reaches a person (SRV-012). Findings with an available fix are patched or rebuilt within a window the owner has set (shorter for critical than for high). Findings with no fix, or judged not exploitable in your setup, are recorded with the reason and a review date. Base images are rebuilt or pulled regularly, not pinned forever.

## Fix
Install trivy following its own documentation, and run the commands above from a systemd timer or cron job at a quiet hour, writing a dated report and mailing only when something new appears. Fix findings by updating the OS (`apt`), pulling newer images and recreating containers (`docker compose pull && docker compose up -d`), and updating lock files for application dependencies. Treat a reported "fixed version" with care on Debian and Ubuntu, which backport patches without raising upstream version numbers; compare against the distribution's security tracker before deciding.

## Risk and rollback
Scanning a full root filesystem uses CPU and disk I/O and downloads a vulnerability database, so run it at low priority (`nice`) off-peak. Updating images or libraries can break an application; keep the previous image tag so you can go back, and update one service at a time. Scanners also report false positives; do not accept a clean report as proof of security. Rollback: disable the timer, or redeploy the earlier image tag.
