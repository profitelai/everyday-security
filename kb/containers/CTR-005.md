# CTR-005 · The Docker socket is never mounted into containers and the docker group is treated as root

## Why it matters
Whoever can talk to the Docker daemon can start a container that mounts the host's whole filesystem as root, which is full control of the host. Docker's own security documentation says only trusted users should be allowed to control the daemon. Two common ways this goes wrong: mounting `/var/run/docker.sock` into a container (popular with dashboards, reverse proxies and CI runners), so that compromise of that one web application becomes compromise of the host; and adding ordinary users or service accounts to the `docker` group, which is root-equivalent without needing a password. Mounting the socket read-only does not help, because the API itself is the dangerous part.

## How to test
```bash
docker ps -q | xargs docker inspect --format '{{.Name}}: {{range .Mounts}}{{.Source}} {{end}}' | grep -i docker.sock
grep -rn 'docker.sock' /path/to/compose/projects/
getent group docker
ss -ltnp | grep -E ':2375|:2376'      # daemon API exposed on TCP?
```
Review the group list: every member can become root.

## Pass criteria
No container mounts the Docker socket. If one genuinely must (a documented tool), it is run from a restricted socket proxy that allows only the read-only calls it needs, or the exception is recorded with its owner. The `docker` group contains only administrators who already have root through sudo. The daemon API is not listening on an unauthenticated TCP port; remote access uses SSH or TLS with client certificates.

## Fix
Remove the socket volume line from Compose. Replace tools that need the API with ones that do not (a reverse proxy configured from files, a deploy done over SSH). For a tool that cannot be replaced, put a filtering socket proxy in front of the socket on an isolated network. Remove non-administrators from the group (`gpasswd -d USER docker`), and give deploy users a narrowly scoped alternative such as a forced SSH command or a pipeline runner outside the production host. Rootless Docker is a stronger design where the host's root is not exposed.

## Risk and rollback
Dashboards, automatic-update tools and auto-discovering proxies stop working without the socket; plan their replacement first. Removing a user from the group takes effect at their next login and can break their deploy scripts; tell them beforehand. Rollback: re-add the mount or the group membership, but record why.
