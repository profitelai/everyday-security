# CTR-003 · Containers run as a non-root user

## Why it matters
By default the main process of a container runs as root inside it. That root is the same user ID 0 as on the host, only fenced in by namespaces and capabilities. If an attacker takes over the application (for example through a file-upload or injection flaw), running as root hands them more to work with: writing anywhere in the container, installing tools, and reaching more kernel features in a container-escape attempt. Running as an ordinary user removes much of that. See SRV-007 for the same principle applied to host services.

## How to test
```bash
docker ps -q | xargs docker inspect --format '{{.Name}} user={{.Config.User}}'
docker exec CONTAINER id -u             # 0 means root
docker info --format '{{.SecurityOptions}}'    # shows rootless or userns when the daemon uses them
```
An empty `user=` means the image default applies, which is usually root. Also run `docker compose config | grep -n 'user:'` to see what the Compose files set, and `grep -n '^USER' Dockerfile` for images you build.

## Pass criteria
Application containers report a non-zero user ID, set either in the image (`USER` instruction) or in Compose (`user: "1000:1000"`). Any container that must run as root (some images only start a service as root and then drop privileges themselves) is listed with a reason. Bonus: the daemon runs in rootless mode or with user-namespace remapping, so even root in a container is not root on the host.

## Fix
In your Dockerfile create a user and switch to it (`RUN adduser ...` then `USER app`). For third-party images, check their documentation for the supported non-root setting, and set `user:` in Compose. Make writable directories and volume mounts owned by that user (`chown` in the image, or `docker run --rm -v VOL:/data busybox chown -R 1000:1000 /data` once). Official images for common databases already drop to a service user; leave their entrypoints alone. Consider rootless mode or `userns-remap` as a second layer.

## Risk and rollback
Switching user often fails first on file permissions (cannot write to a volume, cannot bind port 80). Use a port above 1024 inside the container and publish it as you like. Test in staging or start with one service. Rollback: remove `user:` from Compose and recreate; fix volume ownership back if you changed it. Enabling `userns-remap` changes ownership expectations of all existing volumes and is a larger change; plan it separately.
