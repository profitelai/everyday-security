# CTR-009 · Persistent container data is in known volumes that are included in backups and restore-tested

## Why it matters
Containers are meant to be thrown away and recreated, so anything stored in the container's own writable layer is lost with it. Data you care about (databases, uploads, configuration) lives in volumes or bind mounts. Those are easy to forget when planning backups: a backup that copies the host's home directories but not `/var/lib/docker/volumes`, or a database copied while it is writing, will look fine until the day of the restore. `docker system prune --volumes` and a mistyped `docker compose down -v` can also delete data volumes in seconds.

## How to test
```bash
docker volume ls
docker ps -q | xargs docker inspect --format '{{.Name}}: {{range .Mounts}}{{.Type}}:{{.Name}}{{.Source}}->{{.Destination}} {{end}}'
docker system df -v | head -40
docker compose config | grep -nE 'volumes:|bind'
```
Match the list of volumes and bind-mount paths to your backup job's source list, then check the newest backup for their contents. Ask for the date of the last restore test.

## Pass criteria
Every volume or bind mount holding data you cannot recreate appears in the backup scope, with databases backed up by their own dump or snapshot tool (BAK-006) rather than by copying files under a running server. Backups are encrypted, off the host and follow the rules in BAK-002 and BAK-003. A restore of one container's data has been tested in the last six months (BAK-005). Volumes have meaningful names and no important data is in an anonymous volume.

## Fix
Name volumes in Compose and list them in a short inventory with an owner. Add them to the backup job: a dump command run through `docker exec` for databases, and for plain files a temporary container that mounts the volume read-only and writes a tar archive to a backup directory, a method shown in Docker's volume documentation. Do not run `docker system prune --volumes` or `docker compose down -v` on production without checking what would be removed.

## Risk and rollback
Backing up files from a running service can capture an inconsistent state; stop the container briefly or use the database's native tool. Restore tests must go to a separate location, never over the live volume. Rollback: a backup job is additive; if it causes load, move it to a quieter time.
