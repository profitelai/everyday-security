# CTR-001 · Container images come from trusted sources and are pinned to a tag or digest

## Why it matters
Every image you run is someone else's code running on your host, often with network access to your data. An image from an unknown publisher, or one copied from a random blog post, can contain a miner or a backdoor from day one. A tag such as `latest` is also a moving label: the publisher (or an attacker who takes over their account) can point it at different content tomorrow, so the same Compose file can silently start different software after the next pull. Pinning a version, or better a digest, makes what you run reproducible and reviewable.

## How to test
List what is actually running and where each image came from.
```bash
docker ps --format '{{.Names}}\t{{.Image}}'
docker compose config --images          # run in each project directory
docker image inspect --format '{{.RepoTags}} {{.RepoDigests}}' IMAGE
```
For every image answer three questions. Is the publisher known (a Docker Official Image, a Verified Publisher, or your own registry)? Is the reference a specific version or digest (`postgres:16.4`, or `name@sha256:...`) rather than no tag, `latest` or a bare major tag you did not choose? Does the Dockerfile for images you build start from such a pinned base (`grep -n '^FROM' Dockerfile`)? Images with no registry host and a random user name (`someuser/tool`) need a written reason.

## Pass criteria
Every running image comes from a publisher you can name, and each Compose file and Dockerfile refers to a specific version tag or digest, not `latest` or an untagged name. Images from individuals or unknown publishers are absent or have a recorded decision (who reviewed the source, when). Self-built images use a pinned base image.

## Fix
Replace floating references with a version tag in the Compose file (`image: nginx:1.27.2`), or add the digest for stronger assurance (`image: nginx:1.27.2@sha256:...`, with the digest read from `docker image inspect`). Prefer Docker Official Images and Verified Publishers, or build from source you have read. Keep the version in one place so that updates are a deliberate edit that shows up in review (see CTR-002 for the update routine). Compose file changes should be reviewed like code before `docker compose up -d`.

## Risk and rollback
Pinning means you will no longer receive fixes by accident; the cost is that you must update on purpose, which CTR-002 covers. Changing a tag to a different version can change data formats (databases especially), so back up first (CTR-009). Rollback: put the previous tag or digest back in the Compose file and run `docker compose up -d`.
