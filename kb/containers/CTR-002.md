# CTR-002 · Images are scanned for known vulnerabilities, findings are triaged by a written rule, and images are rebuilt regularly

## Why it matters
An image bundles an operating system's packages and your application's libraries, frozen at build time. Unlike a host, it does not update itself: a container started from a two-year-old image still carries every flaw found since. Scanning shows what is known; without a rule for what to do with the results, teams either drown in hundreds of low-risk findings or stop looking. Related host-level scanning is covered by SRV-011; this check is about the images you run and the routine that replaces them.

## How to test
Scan every image in use, for example with Trivy or Docker Scout.
```bash
docker ps --format '{{.Image}}' | sort -u | while read -r i; do
  echo "== $i"; trivy image --severity HIGH,CRITICAL --ignore-unfixed "$i"
done
docker scout cves IMAGE              # alternative if Docker Scout is available
docker image inspect --format '{{.Created}}' IMAGE
```
Then ask to see the triage rule and the date of the last scan. Check the image creation dates: an image that has not been rebuilt or re-pulled for many months is a finding even if the scanner is quiet.

## Pass criteria
A scan of all running images happens on a schedule (at least weekly) or in the build pipeline, and the result reaches a person. A written rule says what happens to findings, for example: critical or high with a fix available is updated within a stated number of days; findings with no fix are reviewed and either accepted in the ignore file with a reason and expiry date, or mitigated; everything else is handled in the normal update cycle. Images are rebuilt or re-pulled on a routine at least monthly, and sooner when a critical fix applies.

## Fix
Run the scanner from a timer or CI job and send the summary to the alert channel used in SRV-012. Write the triage rule in one paragraph and keep accepted exceptions in a `.trivyignore` file with a comment per entry. Update by changing the pinned version (CTR-001), pulling and recreating: `docker compose pull && docker compose up -d`. For images you build, rebuild with `docker build --pull` so the base image is refreshed, and prefer small base images that carry fewer packages.

## Risk and rollback
Recreating a container restarts the service, so schedule it in a quiet period and check the healthcheck afterwards (CTR-010). A newer image can change behaviour; back up volumes first (CTR-009). Scanners produce false positives and miss unknown flaws, so a clean scan is not proof of safety. Rollback: restore the previous pinned tag and run `docker compose up -d`.
