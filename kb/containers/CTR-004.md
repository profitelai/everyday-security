# CTR-004 · Containers are not privileged, drop capabilities, block privilege gain and use a read-only root filesystem where possible

## Why it matters
A container is only as isolated as its settings allow. A privileged container gets nearly all kernel capabilities and access to host devices, so it is close to running directly on the host; breaking out of it is trivial. Sharing the host's network, process or IPC namespaces, or adding capabilities such as `SYS_ADMIN`, weakens the fence in smaller ways. Dropping capabilities, setting `no-new-privileges` (which stops setuid programs from gaining rights) and making the root filesystem read-only limit what an attacker can do after they get code running inside a service.

## How to test
```bash
docker ps -q | xargs docker inspect --format \
 '{{.Name}} priv={{.HostConfig.Privileged}} capadd={{.HostConfig.CapAdd}} capdrop={{.HostConfig.CapDrop}} secopt={{.HostConfig.SecurityOpt}} ro={{.HostConfig.ReadonlyRootfs}} net={{.HostConfig.NetworkMode}} pid={{.HostConfig.PidMode}}'
docker compose config | grep -nE 'privileged|cap_add|cap_drop|security_opt|read_only|network_mode|pid:|devices'
```
Look for `priv=true`, `net=host`, `pid=host`, added capabilities, and the absence of `no-new-privileges` in the security options.

## Pass criteria
No container is privileged or shares the host's PID or IPC namespace. `network_mode: host` and device mappings appear only where documented. Each service sets `cap_drop: [ALL]` and adds back only the specific capabilities it needs (or has a documented reason not to), has `security_opt: ["no-new-privileges:true"]`, and uses `read_only: true` with `tmpfs` or volumes for the few writable paths. Where read-only is impractical (some databases and CMS images), the exception is written down.

## Fix
In Compose, per service:
```yaml
services:
  app:
    cap_drop: [ALL]
    cap_add: [NET_BIND_SERVICE]   # only if needed
    security_opt:
      - no-new-privileges:true
    read_only: true
    tmpfs: [/tmp]
```
Find the minimum set by dropping everything, starting the service, and reading its error messages. Replace any `privileged: true` with the specific device or capability actually required.

## Risk and rollback
Dropping capabilities and a read-only filesystem commonly break services that write to unexpected paths or change file ownership at start-up; the failure shows in `docker logs`. Introduce one service at a time and keep the previous Compose file. Rollback: remove the added keys and run `docker compose up -d`.
