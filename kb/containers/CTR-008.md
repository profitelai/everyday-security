# CTR-008 · Compose stacks are on separate networks and only the services that must talk to each other share one

## Why it matters
Containers on the same Docker network can reach each other's ports freely, with no firewall in between. If every project on the host sits on one shared network (or on the default bridge), a compromised blog container can connect straight to the database of an unrelated customer app. Segmentation limits the blast radius: a database should be reachable only from the application that uses it, and nothing else. This is separate from what is published to the outside world, covered in SRV-004.

## How to test
```bash
docker network ls
docker network inspect NETWORK --format '{{range .Containers}}{{.Name}} {{end}}'
docker ps -q | xargs docker inspect --format '{{.Name}}: {{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'
docker compose config | grep -nE 'networks:|external:|network_mode'
```
Look for many unrelated containers on one network, containers on the default `bridge`, and databases sharing a network with public-facing services of other projects.

## Pass criteria
Each Compose project uses its own user-defined network by default. Cross-project connections happen only through an explicitly named shared network that contains just the two parties (typically the reverse proxy and the apps it fronts). Databases and caches sit on a backend network used only by their application, flagged `internal: true` where they need no outbound access. No container uses `network_mode: host` without a documented reason.

## Fix
Give each stack its own network, and split networks inside a stack (`frontend` for the proxy and web service, `backend` with `internal: true` for the database). For a reverse proxy serving several apps, create one external network per app and attach the proxy to each, instead of one network holding everything. Use service names for connections, not published ports on the host. Where a service allows it, add a password to the database even on a private network.

## Risk and rollback
Moving containers between networks changes their addresses and breaks hard-coded IPs; connect by service name. An `internal: true` network blocks outbound internet for services on it, which breaks update checks and webhooks. Rollback: attach the service to its previous network in Compose and recreate it.
