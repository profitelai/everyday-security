# CTR-006 · Secrets are not baked into images or stored in Compose files and env files in git

## Why it matters
Container workflows invite shortcuts: a database password typed into `docker-compose.yml`, an `.env` file committed so the team can start the stack, an API key written in a Dockerfile `ENV` or `ARG` line. Image layers keep every earlier instruction, so a secret added and then deleted is still in the image history, and anyone who can pull the image can read it. Environment variables are visible through `docker inspect` and to every process in the container, and often end up in logs and crash reports. Secrets in a git repository persist in its history even after the file is removed. See SRV-009 for the repository side.

## How to test
```bash
docker history --no-trunc IMAGE | grep -iE 'password|secret|token|key'
docker inspect --format '{{range .Config.Env}}{{println .}}{{end}}' CONTAINER | grep -iE 'pass|secret|token|key'   # output is sensitive: do not paste it into tickets
docker compose config | grep -inE 'password|secret|token|api[_-]?key'
git ls-files | grep -E '(^|/)\.env'            # env files tracked in git
git log --all --oneline -- '*.env' | head
```
Also check `.gitignore` and `.dockerignore` for `.env` and key files, and look at file permissions on env files on the server.

## Pass criteria
No credential appears in image history, Dockerfiles, or Compose files committed to git. Env files with real values are not tracked, are mode 600 or 640 and owned by the deploying account. Sensitive values reach containers as file-based secrets (Compose `secrets:` mounted under `/run/secrets/`, read by the application via a `*_FILE` setting or its own file support), or from a secrets manager. Any secret that has appeared in git or an image was rotated.

## Fix
Define the secret in Compose with `secrets:` pointing at a file kept outside the repository, grant it only to the services that need it, and configure the application to read the file (many official images support variables such as `POSTGRES_PASSWORD_FILE`). Use build secrets (`RUN --mount=type=secret`) instead of `ARG`/`ENV` when a build needs a credential. Add the env file and secret files to `.gitignore` and `.dockerignore`, commit a `.env.example` with placeholders instead, and enable secret scanning in your git host or pipeline. Rotate anything that leaked.

## Risk and rollback
Rotating a database or API credential requires changing it in both the service and its clients at the same time; do it in a quiet window. Rewriting git history is disruptive and does not undo exposure, so rotate first and treat history cleanup as optional. Rollback: keep the old credential valid for a short overlap during rotation, then revoke it.
